## 二、题目与解答

### 1. 请做一下自我介绍

答案：我叫李东阳，来自西安交通大学，具备 Java 后端开发和 AI 应用开发经验。平时会主动探索 Rust，并尝试用 Rust 参与或开发开源项目。

我有一段企业内部系统的全栈开发实习经历，准备重点介绍两个项目：一个 Coding Agent 项目，以及一个知识库项目。

### 2. 这个岗位更偏后端，还是偏全栈和 Agent 开发

答案：面试官说明，岗位整体更偏后端，同时可能涉及一部分 Agent 相关开发。候选人的经历与团队需求有一定匹配度。

### 3. 请介绍一下你的实习经历和主要工作

答案：实习公司主要承接大型建筑和交通枢纽相关的信息化项目，例如南京东站相关系统。我参与了内部 ERP 系统和一个内部称为“大 S 系统”的项目，工作内容偏全栈，涉及 Java 后端和 React 前端。前端开发中较多使用了 AI Coding 工具。

### 4. 刚接手项目时，为什么项目无法正常启动？你如何处理

答案：主要原因是数据库结构维护不规范。代码版本和数据库结构经常不一致，历史 SQL 分散在项目文档中，也有人修改表结构后忘记补充脚本。

我将历史变更整理为 Liquibase 的 changelog 和 changeSet，让 Spring Boot 启动时检查已执行的数据库变更，并自动执行尚未应用的 SQL。接手后的第一周主要用于梳理和整合这些历史变更。

### 5. Liquibase 在这个项目中具体解决了什么问题

答案：Liquibase 会读取 changelog，并根据数据库中保存的执行记录判断哪些 changeSet 已经运行。未执行的变更会在项目启动时按顺序应用，避免旧数据库缺少表结构变更而导致项目启动失败。

这个问题在外包项目中较突出，因为不同环境中的代码版本和数据库结构长期缺少统一维护。

### 6. 你提到的“大 S 系统”是什么

答案：它不是通用技术概念，而是实习公司内部的一套系统。大型项目会产生大量表名、方法名、文档和配置，这套系统用于集中管理和维护这些项目资料及相关开发内容。

### 7. 为什么把原来的外部翻译接口替换为本地模型

答案：原方案调用外部的百度翻译接口，存在调用成本，而且方法名翻译效果不理想。我将其替换为本地部署的通义千问模型 API，用于把中文名称转换为英文方法名。

事后复盘时，我认为可以用策略模式同时保留新旧实现，并加入降级能力；但导师认为旧接口不再需要，因此当时没有继续做兼容。

### 8. 接入 Nacos 时遇到了什么问题

答案：项目需要从 Nacos 读取配置，但最初一直无法连接。我根据报错和资料排查了两三个小时，最后确认是 Nacos 1.x 与 2.x 的端口及底层通信方式发生变化，当前配置与实际版本不匹配。

定位问题后，我整理了一份文档并向导师汇报。

### 9. 请用代码简单说明策略模式

答案：我的思路是先定义统一策略接口，接口提供策略标识和具体执行方法；再由两个实现类分别完成不同策略。运行时用 Map 按策略名称保存实现，根据输入参数选择对应实例并执行。

面试官反馈：现场代码表达较乱。在 Spring 中可以将同一接口的多个 Bean 注入为 List 或 Map，再根据运行参数选择指定实现。

### 10. Spring Boot 和 Spring 容器是什么关系

答案：Spring Boot 建立在 Spring 之上，仍然使用 Spring 的 IoC 和依赖注入能力。在该策略模式场景中，可以从容器获取同一接口的多个 Bean，并在 CommandLineRunner 等初始化逻辑中建立策略映射。

面试表现记录：候选人的现场回答较零散，核心意思是通过 Spring 容器管理和获取策略实例。

### 11. Nacos 通常用于哪些场景

答案：Nacos 可以用于服务注册、服务发现和配置管理。服务实例上下线时，注册中心可以更新实例信息；应用也可以从 Nacos 集中读取配置。

### 12. 注册中心应该选择 CP 还是 AP

答案：候选人最初把问题展开到配置一致性、Redis、锁和并发控制，没有直接回答 CP 与 AP 的取舍；随后表示相关知识没有复习充分。

面试官反馈：服务注册场景通常更重视可用性和分区容错性，不一定追求强一致性。回答问题时不建议用表面相关的知识强行解释另一个概念。

### 13. 你如何理解 Coding Agent 的 Harness

答案：我把 Coding Agent 理解为 Agent Loop 加 Harness。Agent Loop 负责持续执行观察、思考和行动；Harness 则负责让 Agent 能稳定运行，包括安全控制、记忆管理、上下文压缩、工具约束等工程能力。

### 14. 你的 Agent 如何设计记忆和上下文压缩

答案：我设计了三层压缩机制。

1. **大文件压缩**：Read 工具读取的内容超过阈值时，将正文落盘，上下文只保留文件路径和元数据。
2. **单轮工具输出压缩**：一轮对话中工具输出过大时，将体积最大的结果落盘，使本轮内容保持在限额内。
3. **长期上下文压缩**：上下文接近阈值时，最近十轮原样保留，更早的内容由大模型摘要后再放回上下文。

### 15. 你在使用现有 Coding Agent 时发现了哪些问题

答案：主要发现了三类问题。

1. **API 兼容问题**：我曾发现 Codex 接入 DeepSeek API 时会异常中断。排查后认为，DeepSeek 的推理内容字段和流式结束事件与 OpenAI 接口存在差异，而调用方只检查 `content` 和 Tool Call 等字段，导致结束状态判断不一致。
2. **子 Agent 调度问题**：Claude Code 更常主动使用子 Agent，而 Codex 通常需要明确提示；有时提示词中只要出现 `sub-agent`，也可能触发不符合本意的调用。
3. **工具选择问题**：我观察到某些 Coding 工具会为简单文档修改先写 Python 脚本，再分块循环处理，路径过于绕。我的改进是在工具层增加优先级，让直接 Read 和 Write 的优先级高于 Bash 或临时 Python 脚本。

### 16. 你如何设计子 Agent 与主 Agent 的同步

答案：我将子 Agent 封装为工具调用。主 Agent 不必一直阻塞等待，而是让子 Agent 的结果先写入共享消息区域；主 Agent 每轮循环检查是否有新结果，再决定是否合并。

在此基础上，我增加了汇报策略，可以控制子 Agent 的汇报时机。暂停汇报时，子 Agent 不打断主 Agent；开启后，新结果会进入主 Agent 的等待区，并触发后续循环。

### 17. 你觉得自己的 Agent 比 Codex 或 Claude Code 更好用吗

答案：我没有直接判断它更好用。当前版本带有 UI，可以查看每个子 Agent 的任务状态和 Agent Team 页面，但前端完成度不高，实际使用体验仍不理想。

### 18. SSE 和普通 HTTP 请求有什么区别

答案：我的理解是，SSE 在建立 HTTP 连接后，可以由服务端持续以流式方式返回事件，适合连续输出内容；普通的一次性 HTTP 请求通常在完成一次响应后结束。

### 19. SSE 和 WebSocket 有什么区别

答案：WebSocket 支持客户端与服务端双向实时通信；SSE 主要是服务端向客户端的单向流式推送。

现场回答中，我把 SSE 与轮询混在了一起，并认为 SSE 需要客户端按间隔不断请求，这部分表述不够准确。

### 20. AI 对话和 Coding Agent 场景中，你会如何选择 SSE 与 WebSocket

答案：我当场更倾向使用 WebSocket，理由是双向通信和实时性更强，但需要处理连接稳定性和重连。对于仅需要服务端持续返回内容的单向流式场景，会考虑 SSE。

### 21. Elasticsearch 和 MySQL 的索引有什么区别

答案：MySQL 常用 B+Tree 索引，适合等值查询、组合索引和范围查询。Elasticsearch 主要使用倒排索引，将分词后的关键词映射到文档，更适合全文检索和关键词搜索。

### 22. 给定一棵二叉搜索树，如何返回任意两个不同节点值之间的最小绝对差

答案：最初我想到遍历整棵树、收集所有节点值、排序后再计算相邻元素差值。在面试官提示这是二叉搜索树后，我意识到中序遍历会直接得到有序序列，因此只需比较相邻节点值即可得到最小差值。

### 23. 算法题的现场实现还有哪些问题？能否进一步优化

答案：现场实现包含构建树、中序遍历生成数组、再遍历数组求最小差值三个步骤。面试官指出代码中的 `isHead` 状态一直为 `true`，初始化逻辑存在遗漏。

此外，可以在中序遍历时维护前一个节点值和当前最小差值，从而一次遍历完成计算，不必额外保存完整数组。

### 24. 项目大多与 AI Agent 有关，会不会显得 Java 基础不足

答案：面试官认为整体还好。从现场代码和基础知识问答来看，候选人具备一定 Java 基础；当前很多简历都在向 AI 应用和 Agent 靠拢，这本身不是明显问题。

面试官也说明，自己暂时难以准确判断当前社招和校招对 Agent 项目的统一要求。

### 25. 团队主要负责哪些工作

答案：团队主要负责小红书 ToC 活动平台的后端开发，包括站内事件订阅、活动规则判断和奖励发放。团队也承接世界杯等赛事相关项目和基础数据建设。

另一部分工作面向社区内容运营，涉及创作者和笔记挖掘、与创作者建联、内容管理及创作者扶持，并探索用 AI 或 AIGC 提升内部运营效率。
