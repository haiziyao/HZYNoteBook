# 快手电商后端一面问答整理

> [!info] 面试信息
> - 候选人：李东阳
> - 面试时间：2026年9月9日
> - 面试方向：快手电商后端

本次面试围绕 Java 后端与 AI Agent 项目经历展开，重点讨论 Agent 循环、多 Agent 协作、工具与权限系统、上下文和记忆管理，并包含一道连续子数组算法题及团队业务介绍。

## 一 个人背景与项目概览

### Q1 请做一下自我介绍

**A：** 面试官您好，我叫李东阳，来自西安交通大学。我具备 Java 后端开发和 AI Agent 应用开发经验，平时也学习 Rust，做过相关项目，并在 GitHub 上获得过一些 Star。

我有一段企业内部系统开发实习经历，所在公司类似国企外包性质的建筑企业。我负责全栈开发，但工作更偏后端。今天主要准备了两个项目：一个 Coding Agent 项目和一个知识库项目。

### Q2 你的 Coding Agent 项目主要解决什么问题 你做了哪些改进

**A：** 我在使用现有 Coding Agent 时遇到了一些问题，因此从底层实现了一个原生 Java 版本，主要做了三类改进。

1. 处理 DeepSeek API 在思考模式下可能导致 Agent 循环异常中断的问题。
2. 改进 Sub-agent 的结果汇报机制，支持不主动汇报、自动汇报和按需手动汇报。
3. 为工具系统增加优先级，优先使用直接的 `read`、`write` 等工具，降低不必要地调用 Bash 或临时 Python 脚本的概率。

记忆系统和上下文压缩主要参考了开源项目。

## 二 Agent 循环 工具与多 Agent 协作

### Q3 DeepSeek API 为什么会导致 Agent 循环中途结束 你如何定位这个问题

**A：** 我发现 Codex 接入 DeepSeek API 后，有时无法完成一轮完整的 Agent loop。排查后认为问题出在结束条件判断：现有逻辑主要检查 `content` 和 `tool call` 是否有内容；如果两者都为空，就可能判定本轮结束。

DeepSeek 开启思考模式后，还会返回 `reasoning_content`。某些响应里 `reasoning_content` 有内容，但 `content` 和 `tool call` 为空，因此被误判为已经结束。我使用 Postman 直接测试了 SSE 响应，并观察到 DeepSeek 会在流结束时发送明确的结束标识，据此确认了兼容性问题。

### Q4 你观察到的 Sub-agent 调用方式有哪些 你的汇报机制如何设计

**A：** 常见实现有两种：

1. 把 Sub-agent 当作工具同步调用，主 Agent 阻塞等待最终结果。
2. 让 Sub-agent 完成后把结果写到共享位置，主 Agent 在每次请求前检查并取回结果。

我的实现把 Sub-agent 封装为工具，并增加了汇报控制。用户可以选择不把 Sub-agent 内容自动加入主 Agent 上下文，也可以开启自动汇报，或在主 Agent 运行到某个阶段时手动触发汇报。Sub-agent 只向主 Agent 同步最终结果，不同步每一步中间推理。

### Q5 为什么要给工具设置优先级

**A：** 我使用 WorkBuddy 修改一个 Markdown 文件时，发现它先读取文件，随后却编写 Python 脚本处理文本，甚至把内容拆成元组后循环写入新文件。工具调用报错后，它又长时间反复尝试，整个任务运行了三十多分钟。

我认为根因是工具系统没有明确优先级。`read`、`write` 等直接工具应优先使用，Bash 或临时 Python 脚本的优先级应更低，因此我在自己的项目中加入了工具优先级。

### Q6 一轮完整的 ReAct 流程是怎样实现的

**A：** 系统先组装系统提示词、用户消息和工具信息，再向模型发起流式 SSE 请求。客户端逐段解析并拼接响应，然后判断是否存在 `tool call`。

如果没有工具调用，本轮结束并输出答案；如果存在工具调用，就执行对应工具，把工具结果写回消息上下文，再发起下一轮模型请求，直到模型不再请求工具。

### Q7 模型如何知道可以调用哪些工具 如果工具有几千个怎么办

**A：** 工具的名称、描述和参数格式会作为上下文提供给模型，模型在响应的 `tool call` 字段中给出要调用的工具和参数。

为避免一次性注入几千个工具的完整描述，我为工具接口增加了是否渐进式披露的配置。需要渐进式披露的工具只在初始提示词中保留元信息；模型需要具体工具时，先调用 `tool search`，再获取该工具的完整说明。

### Q8 这个 Agent 使用了什么技术栈和框架

**A：** 项目使用原生 Java 实现，没有使用 LangChain 等 Agent 框架。

### Q9 主 Agent 与 Sub-agent 如何交互

**A：** Sub-agent 被封装成一个工具。调用后，它在自己的 ReAct loop 和独立上下文中运行，并把最终结果写到主 Agent 可访问的位置。主 Agent 在每次 ReAct 请求前检查该位置，有结果时再合并到自己的上下文。

Sub-agent 的中间步骤不会逐轮发送给主 Agent。它完成任务后才写入最终结果；如果主 Agent 判断结果不合适，可以再次调用 Sub-agent，或在主 Agent 自己的 ReAct loop 中继续处理。

### Q10 如何判断 Sub-agent 已完成 是否设置最大循环次数

**A：** Sub-agent 在停止前写入最终结果。我给推理步数设置过较高的默认上限，大约两百到三百步，实际测试通常达不到该上限。主 Agent 会像判断普通工具结果一样判断 Sub-agent 的结果是否可用。

面试官追问了结果持续错误时可能出现空跑和成本失控的问题。我当时的回答是测试中没有遇到过，并认为模型在连续失败两三次后通常会调整策略。在一次 SWE-bench 题目测试中，任务运行约两个小时，并通过了约两百到三百个测试点。不过，这套设计没有更严格的失败次数、超时或成本上限。

### Q11 MCP 和 Skill 有什么区别

**A：** MCP 是一种协议，更偏向把外部工具或完整操作流程封装成可调用能力，例如远程执行 GitHub 或内容平台的一系列操作。Agent 本地不必重新实现整套流程，只需要通过协议调用。

Skill 更偏向本地可复制的知识和工作流程，通常用于承载提示词、文档说明和不能直接抽象成 tool 的操作方法。MCP 是协议层，Skill 是增强 Agent 能力的具体内容载体。

### Q12 一个 Skill 通常包含哪些内容

**A：** 至少需要一个 `SKILL.md`，用来说明目标、步骤和约束。有些 Skill 还会附带 Python 等脚本，帮助 Agent 更稳定地执行具体操作。我主要见过这两部分。

## 三 上下文 记忆 权限与状态

### Q13 超长工具输出如何自动落盘 摘要如何生成

**A：** 每次工具调用后，系统会用字符数与 token 数约二比一的经验比例估算输出规模。以 `read` 工具为例，如果估算结果超过 20K token，就把输出沉淀成文档，避免直接占满上下文。

摘要功能当时尚未完成。测试一个约 5 MB 的文档时，直接把全部内容载入上下文再压缩效果不好，因此我把 `read` 工具改为每次最多读取两千行并保存游标。落盘内容主要保留文件名、基础信息和前约一百行。

### Q14 历史消息如何压缩 压缩结果保留哪些信息

**A：** 系统保留最近十轮对话。当上下文接近约 200K 的上限、剩余空间约 20K 时，会把更早的消息拼接起来，再调用一次模型生成压缩摘要，并把摘要加入新的上下文。

压缩提示词要求尽量保留用户意图、当前目标、已完成任务、未完成任务和用户强调的必要条件。我没有规定严格的摘要格式，用户长期习惯由另一套记忆机制处理。

### Q15 危险命令拦截和权限控制如何实现

**A：** 设计分为五层：

1. 命令黑名单和正则匹配，例如拦截 `rm -rf`。
2. 把命令工作目录解析为实际路径，并检查它是否位于当前项目路径内。
3. 提供只读、可写和全部允许等权限模式。
4. 在系统提示词中再次约束禁止执行的命令。
5. 人在回路：当当前权限不足时，系统向用户请求确认。

### Q16 除 rm -rf 外 其他危险命令如何维护

**A：** 危险命令主要保存在独立文件中，工具执行前通过正则匹配；提示词只放少量核心限制。初版命令列表由 Agent 生成，规模较大，我没有逐项完整审核。

### Q17 Sub-agent 的权限如何处理 高风险操作由谁确认

**A：** Sub-agent 继承主 Agent 的权限。如果主 Agent 是全部放行，Sub-agent 也全部放行；如果主 Agent 要求每次执行前询问，Sub-agent 的权限请求也会传给用户确认。Sub-agent 的中间推理保留在自己的 loop 中，最终结果才同步给主 Agent。

### Q18 一个完整的 Agent 由哪些模块组成

**A：** 第一部分是 conversation manager，负责会话、历史消息和上下文。第二部分是模型调用客户端。第三部分是系统提示词的构建与注入，包括基础 system prompt、工具定义、Skill 定义、项目级记忆和全局记忆。

此外还需要工具调用能力，以及调用工具前后等阶段的 hook 接口。Sub-agent 本质上也是一个完整的 ReAct Agent，只是与主 Agent 存在从属关系，并使用独立的上下文。

### Q19 用户记忆如何识别 持久化和加载

**A：** 每轮对话后，系统会额外调用一次模型，判断用户消息是否值得记忆。例如用户指定使用 Java 21，这类偏好会被抽取并落盘。

项目级记忆使用 JSONL 文件保存，每条记忆一行，并通过关键词匹配加载。我的格式约束比较弱，内容类似“Java 版本：Java 21”。会话上下文则按 Session 形式持久化，压缩摘要也会保存到磁盘。

### Q20 面试官指出了记忆和上下文管理中的哪些问题

**A：** 主要有三个问题：

1. 如果只保存用户消息，不保存模型建议及用户对建议的确认，就可能丢失语义。例如模型建议 Java 18、用户回答 yes，若只记录用户偏好 Java 21 和 yes，系统无法恢复最终采用 Java 18 的事实。我确认当时没有考虑到这一点。
2. 摘要没有建立可检索的轮次、主题或意图索引，因此无法准确判断用户是在引用第十一轮还是第十二轮的信息。
3. 固定保留最近十轮并不区分消息价值；如果十轮都是闲聊，当前实现仍会保留它们。

以上场景主要依赖模型对上下文自行判断，尚未形成完善机制。

### Q21 Checkpoint 和状态恢复是如何实现的

**A：** 实现比较粗糙。Checkpoint 本质上是保存完整的对话 Session；恢复时读取该 Session，或者创建一个新 Agent，再用已保存的 conversation manager 数组替换新 Agent 的会话状态。没有设计更细粒度的状态机。

## 四 算法题与团队业务

### Q22 给定一个整数数组 找出和最大的连续子数组并返回最大和

**A：** 我的思路是使用前缀和。遍历数组时维护当前位置之前的最小前缀和，用当前前缀和减去最小前缀和，得到以当前位置结尾的最大子数组和，再更新全局最大值。关键是最小前缀和必须出现在当前前缀和之前。

现场编码时因为较久没有使用当时的编辑模式并遇到报错，没有完整展示代码。面试官表示主要查看代码结构，随后结束了算法环节。

### Q23 快手电商该团队主要负责哪些业务

**A：** 团队负责快手电商商城经营相关业务，主要分为 B 端和 M 端。

**B 端：** 面向商家，提供商家经营和商品运营能力，例如新商引入、爆品运营、新品成长，以及商品发布过程中的素材优化和问题诊断，包括缺少主图、主图模糊等可能影响交易的问题。

团队也会使用大模型为商家或运营人员提供问答入口，减少重复答疑，并生成图片、视频、商品主图和卖点等内容。

**M 端：** 主要服务管理者和运营人员。管理者通过平台了解运营任务完成情况；运营人员管理多个商家，需要经营洞察、任务跟踪、投流异常和数据下滑原因分析等能力。
