## 一、一句话说清这个需求

现在给一张表生成知识，系统只会**认领已有的指标/维度**；智能模式要让 LLM **提出新的指标/维度（以及 SQL 模板）**，但这些新东西必须**人工逐条确认**后才算数。

---

## 二、它要解决什么问题

### 1. 现状（标准模式）

用户在知识管理页输入表名，系统做三件事：

1. 从 Keeper 拿表结构，建 DT（表）和 FIELD（字段）
2. 给每个字段在**本域已有**的 MET（指标）/DIM（维度）里找一个绑上（BIND_MEANING 关系）
3. 直接落库

问题出在第 2 步：**找不到就不绑**。

### 2. 举个例子

域：直播域，刚建，里面只有 2 个指标。

| 字段 | 业务含义 | 本域有没有对应知识点 | 标准模式结果 |
|---|---|---|---|
| `play_cnt` | 播放次数 | 有：〔指标〕播放次数 | 绑上 |
| `gift_amt` | 送礼流水 | 没有 | **不绑，空着** |
| `reg_chan` | 注册渠道 | 没有 | **不绑，空着** |
| `platform` | 平台 | 通用域有，本域没有 | **不绑，空着** |

结果：一张 20 个字段的表，可能只绑上 2 个。域 Owner 要自己手工建"送礼流水""注册渠道"，再一个个去绑。

### 3. 智能模式想达到的效果

同一张表：

| 字段 | 智能模式结果 | 页面标签 |
|---|---|---|
| `play_cnt` | 绑到已有〔指标〕播放次数 | 🔵 匹配已有 |
| `gift_amt` | LLM 提议新建〔指标〕送礼流水 | 🟢 新增 |
| `reg_chan` | LLM 提议新建〔维度〕注册渠道 | 🟢 新增 |
| `platform` | 若勾选了通用域，绑到〔维度〕平台维度·通用域 | 🔵 匹配已有 |

另外再给出这张表"怎么用"：

| 高频查询模板 | 产出指标 |
|---|---|
| 🟣 直播间播放统计（`SELECT room_id, SUM(play_cnt) ...`） | 直播间播放量、直播间独立观众数 |

用户在一个页面里逐行点「采纳 / 丢弃」，最后点「确认入库」。

PRD 原文的三条收益：

- 覆盖率：从"只有物理层"到"物理层 + 逻辑层"
- 工作量：从"手工建 + 逐个绑"到"AI 提议 + 人工确认"
- 发现能力：LLM 能找出人容易漏的指标维度

### 4. 边界（PRD 2.3）

做的：

- 只产 4 类：表、字段、指标、维度（10/16 后加上 SQL 模板）
- 提议新指标/维度，并建好字段绑定

不做的：

- 不跳过人工确认直接发布
- 不碰业务过程（BP）、业务实体（BE）
- 不替代标准模式（标准仍是默认）

## 三、关键概念（先把词对齐）

| 词 | 意思 | 对应代码概念 |
|---|---|---|
| 标准模式 | 表结构 + 匹配已有知识点，直接落库 | 轻量流程 `tableLiteGen` |
| 智能模式 | 标准模式 + LLM 提议新知识点，需确认 | **还不存在** |
| 匹配已有 🔵 | 字段绑到一个已存在的官方 MET/DIM | `BIND_MEANING` 指向存量 atomId |
| 新增 🟢 | LLM 提议新建的 MET/DIM | 入库时新建实体 + `BIND_MEANING` |
| 候选知识点 | 还没入库的"新增"项 | 不在 `tb_atlas_entity` 里，存哪 PRD 未写 |
| 确认清单 | 一张表一份，等人审的草稿 | **还不存在** |
| 高频查询模板 🟣 | 从"高频使用场景"提炼的 SQL 模板 | 实体类型 `SP` |
| 产出指标 | 模板跑出来能得到的指标 | `MET` + `REL_ATOM`（MET → SP） |
| 匹配范围 | 在哪些域里找"已有" | 现在固定只查目标域 |
| 待复核且未上线 | 入库后的状态 | `review_status` + `effective=INACTIVE` |

术语细节查 `docs/glossary.md`。

## 四、用户视角：完整走一遍（每步看数据怎么变）

例子：直播域 Owner 给 `b_dws.dws_live_play_daily` 跑智能模式。表有 5 个字段：`play_cnt`、`gift_amt`、`pay_amt`、`reg_chan`、`platform`。

### 第 1 步：提交

入口：知识管理页 → `[+ 新增表知识 |▾]` 主区 → 输入表名 → 选：

```
生成模式：  ⭕ 标准   ● 智能（10-20 分钟，需人工确认）
匹配范围：  ● 仅本域   ⭕ 本域 + 指定域   ⭕ 不匹配已有
```

点 `[开始生成]`，弹窗关闭，提示去「智能生成管理 → 任务进展」看进度。

提交前逐表校验（详见 5.3 节）。

数据变化：任务进展新增 1 行，状态「生成中」。

### 第 2 步：生成完成，物理层先落库

`tb_atlas_entity` 新增 6 行（1 DT + 5 FIELD），状态未上线：

| atom_type | en_name | domain | effective |
|---|---|---|---|
| DT | b_dws.dws_live_play_daily | live | INACTIVE |
| FIELD | b_dws.dws_live_play_daily.play_cnt | live | INACTIVE |
| FIELD | ...gift_amt | live | INACTIVE |
| FIELD | ...pay_amt | live | INACTIVE |
| FIELD | ...reg_chan | live | INACTIVE |
| FIELD | ...platform | live | INACTIVE |

`tb_atlas_relation` 新增 5 条 `BELONG_TAB`（FIELD → DT）。

**此时还没有任何 `BIND_MEANING`，也没有新 MET/DIM。**

任务进展：状态变「完成」。注意 PRD 定义「完成 = 知识已落库」，不代表用户确认过。

### 第 3 步：生成确认 Tab 出现一份清单

```
▾ b_dws.dws_live_play_daily（表知识 · 5个字段语义 · 1个高频查询模板）

【表知识确认】只读：表名/中文名/分层/粒度/分区/主键/... + 必须过滤条件 → 数据边界 → 使用指南

【字段语义确认】
 play_cnt  播放次数  🔵匹配已有  〔指标〕播放次数·直播域    ● 采纳 ○ 丢弃
 gift_amt  送礼流水  🟢新增      〔指标〕送礼流水            ● 采纳 ○ 丢弃
 pay_amt   实付流水  🟢新增      〔指标〕送礼流水（聚合）    ● 采纳 ○ 丢弃
 reg_chan  注册渠道  🟢新增      〔维度〕注册渠道            ● 采纳 ○ 丢弃
 platform  平台      🟢新增      〔维度〕平台                ● 采纳 ○ 丢弃

【高频查询模板确认】
 🟣直播间播放统计  SELECT room_id, SUM(play_cnt)...  〔指标〕直播间播放量  ● 采纳 ○ 丢弃

                                       [放弃本表结果]  [确认入库]
```

默认全部采纳。悬浮知识点名可看属性卡片（描述、单位、聚合方式）。**表级和字段属性只读，不能在这里改。**

数据变化：库里还是第 2 步的样子。清单存哪 PRD 没写。

### 第 4 步：用户审

假设用户：丢弃 `platform`（`仅本域` 没匹配到通用域的平台维度，LLM 新建了一个，重复了），其余采纳。

### 第 5a 步：点「确认入库」

`tb_atlas_entity` 新增：

| atom_type | en_name | 状态 |
|---|---|---|
| MET | 送礼流水 | 待复核、未上线 |
| DIM | 注册渠道 | 待复核、未上线 |
| SP | 直播间播放统计 | 待复核、未上线 |
| MET | 直播间播放量 | 待复核、未上线 |

`tb_atlas_relation` 新增：

| 类型 | 方向 | 含义 |
|---|---|---|
| BIND_MEANING | play_cnt → 播放次数（存量） | 字段语义 |
| BIND_MEANING | gift_amt → 送礼流水 | 字段语义 |
| BIND_MEANING | pay_amt → 送礼流水 | **⚠️ 撞 D-13，见 6.6 节** |
| BIND_MEANING | reg_chan → 注册渠道 | 字段语义 |
| DEPEND_TABLE | 直播间播放统计 → DT | 模板依赖表 |
| REL_ATOM | 直播间播放量 → 直播间播放统计 | 指标由模板产出 |

清单消失。上线还要去知识管理页走现有的复核、发布流程（本需求不管）。

### 第 5b 步：或者点「放弃本表结果」

二次确认"一旦丢弃将不可复原"。

数据变化：第 2 步落的 6 个实体 + 5 条关系一起删除（按项目惯例是逻辑删除 `is_valid=0`）。清单消失。

### 第 6 步：再生成一次会怎样

| 情况 | 结果 |
|---|---|
| 清单还没处理 | 旧清单自动作废，生成完出新清单 |
| 已确认入库过 | 智能模式允许"本域覆盖重生成"，入库前再提醒一次"将覆盖已有表知识" |
| 上次丢弃的候选 | 会再出现，系统不记"已拒绝" |

## 五、规则细节

### 5.1 页面改动（第二章）

| 改动 | 前 | 后 |
|---|---|---|
| 工具栏按钮 | `[冲突管理]` | `[智能生成管理]` |
| 新增知识点 | 独立按钮 `[+ 新增知识点]` | 并进 `[+ 新增表知识 \|▾]` 下拉 |
| 冲突管理弹窗 | 处理属性/关系/重复冲突 | **下线**；只留"重复"一类，二期放进「域知识体检」 |
| 资源管理 Tab | 管理已加的表资源、文档上传 | **下线**；任务记录改到「任务进展」 |
| 智能生成管理页 | 无 | 新增 3 个 Tab：生成确认（默认）/ 任务进展 / 域知识体检（二期占位） |

设计立场（4.2.1 原文）：生成流程里用户只处理"生成确认"一件事，存量治理全推到二期体检。

### 5.2 匹配范围（4.1.1）

| 选项 | 行为 |
|---|---|
| 仅本域（默认） | 只在当前域找 |
| 本域 + 指定域 | 叠加勾选域；默认预勾创作者、稿件、用户、通用、设备、内容消费、流量、互动、内容、图文 |
| 不匹配 | 全部字段直接让 LLM 新建，适合从零建域 |

### 5.3 提交校验（4.1.3）

| 命中 | 标准模式 | 智能模式 |
|---|---|---|
| 表正在生成中 | 拒绝 | 拒绝 |
| 本域已有表知识 | 拒绝 | **允许**，确认后发起；入库时再提醒覆盖 |
| 跨域已有表知识 | 拒绝 | 拒绝（表知识全局唯一） |
| 有未处理清单 | 提示覆盖，确认后可提交 | 同左 |

批量提交时，不逐个弹窗，给一份"可生成 N / 不可生成 M"的分组清单，一次确认。

### 5.4 确认与放弃（4.2.3）

| 行 | 采纳 | 丢弃 |
|---|---|---|
| 🔵 匹配已有 | 建绑定，字段语义以官方为准 | 不绑，字段保留 AI 写的含义 |
| 🟢 新增 | 建知识点（待复核）+ 绑定 | 不绑；该知识点所有关联行都丢了就不建 |
| 🟣 模板 | 建 SP + 产出指标 + 两类关系 | 不建 SP；只被它引用的产出指标也不建 |

整表一次提交，不支持单条提交。

### 5.5 必须记住的四条规则

1. **英文名重复**：生成时不查，入库时和域内已有知识点比，重了就自动加 `_1`、`_2`，不阻塞（评审结论 3）
2. **产出指标不许和字段级指标同名**："播放次数"不行，要写成"直播间播放量"
3. **产出指标一律算新增**，不去匹配已有；重复留给二期体检
4. **同表多个模板产出同一指标**，合并成一个候选

### 5.6 实现节奏（2.4）

| 期 | 内容 |
|---|---|
| P0 | 分裂按钮、生成弹窗、管理页（生成确认 + 任务进展）、提交校验；同步下线冲突管理、资源管理 |
| P1 | 从文档生成知识：识别到表名 → 触发表知识生成；非表内容 → 提炼术语/FAQ/规则等 |
| P2 | 域知识体检：域内全量重复检测，合并时关系自动迁移 |

注意：P0 下线文档上传后、P1 上线前，"从文档生成"没有入口。

### 5.7 评审结论（9-28）

| # | 结论 |
|---|---|
| 1 | "AI 拿不准的问题确认"本期不做，挪到体检 |
| 2 | 失败重试能不能做，待 @不易非 技术确认 |
| 3 | 英文名重复入库时加后缀 |

### 6.2 标准模式 = 轻量流程（重点读）

流程定义：`app/atlas/src/main/resources/processes/tableLiteGen.bpmn20.xml`

```
liteCollect  →  liteMatch  →  liteArchive
 采集表结构      字段匹配       走 ingest 落库
```

每个原子 `async=true`，失败只重试当前原子（R3/PT1M）；业务错误走 `failedEnd`，不重试。

| 原子 | 文件 | 做什么 | 输入 → 输出 |
|---|---|---|---|
| ① liteCollect | `workflow/atom/impl/lite/LiteCollectAtom.java` | Keeper 取表结构 → Collector 解析出 DT + FIELD；没有 DT 直接报错 | `fullTableName`、`targetDomain` → `collectResult` |
| ② liteMatch | `workflow/atom/impl/lite/LiteMatchAtom.java` | 调 `resolveFieldMeanings` 给字段追加 `BIND_MEANING` | `collectResult` → `collectResult`（原地追加） |
| ③ liteArchive | `workflow/atom/impl/lite/LiteArchiveAtom.java` | 适配成 `KnowledgeIngestRequest` → `ingest(request, true, invokeUser)` | `collectResult` → 无 |

几个要看懂的点：

- **落库默认 INACTIVE，不发布**（`LiteArchiveAtom` 类注释）。智能模式"待复核未上线"正好吻合。
- **撞 D-11a 记 SKIPPED 不记 FAILED**（`LiteArchiveAtom.ERROR_ALREADY_EXISTS`）。智能模式要支持本域覆盖，这里要改。
- **适配器的陷阱**（`LiteIngestRequestAdapter.java` 类注释）：本地临时 ID 只能放 `bizId`，放进 `atomId` 会被 ingest 当成存量去 update 不存在的行。智能模式新增 MET/DIM 一样要走这个通道。
- **操作人靠流程变量带**：Flowable 异步线程拿不到请求上下文，见 `docs/lessons/027`。

### 6.3 字段匹配器（"匹配已有"的核心）

文件：`facade/FieldMeaningResolver.java`

三级匹配，按顺序：

1. **HISTORY**：同域历史上同名字段绑过什么，直接复用
2. **EXACT**：字段短名 = 某个 MET/DIM 的 enName
3. **LLM**：剩下的字段一次性交给 LLM，从候选列表里选；选不出返回 `-1`（UNRESOLVED）

LLM 只能"选"，不能"新建"。**智能模式的"新增"就是要在第 3 级之后，再给 UNRESOLVED 的字段加一步"提议新知识点"。**

候选从哪来：`LightweightTableKnowledgeFacadeService.java:348`

```java
new MeaningCandidateSnapshot(knowledgeEntityService.listValidMeaningEntities(domainAtomId))
```

只传了一个 `domainAtomId`。"本域 + 指定域"要从这里改成多域。

### 6.4 提交校验

| 文件 | 内容 |
|---|---|
| `facade/LiteBatchGenValidateService.java` | 三规则判定，只判不拦 |
| `enums/LiteBatchValidateRule` | `RUNNING` > `EXISTS_LOCAL` > `EXISTS_CROSS_DOMAIN`（声明顺序即优先级） |
| `api/http/LiteTableGenController.java` | `POST /atlas/table-gen/lite-batches[/validate]` |
| 文档 | `docs/specs/轻量表建表校验-接口契约与交互流程.md` |

和 PRD 的差异：

| PRD | 现有 | 要做 |
|---|---|---|
| 正在生成中 | `RUNNING`（任意域在跑都拦） | 一致 |
| 本域已有 | `EXISTS_LOCAL` 拒绝 | 智能模式改成允许 + 提醒 |
| 跨域已有 | `EXISTS_CROSS_DOMAIN` 拒绝 | 一致 |
| 有未处理清单 | 无 | 新增规则码 |
| 提交时逐表校验 | **提交侧刻意不校验**（spec §七"用户明确要求"） | 和 PRD 矛盾，要问 |

### 6.5 ingest 统一闸门（入库都走这里）

| 文件 | 看什么 |
|---|---|

### 6.6 两条会挡路的硬规则

**D-13：N:1 唯一**

规则定义：`facade/RelationN1Spec.java:61`

```java
// target 侧违反判定：BIND_MEANING → TABLE_AWARE
```

判定实现：`facade/RelationN1Validator.java` 的 `hasSameTableFieldBoundToTarget`

### 6.7 完整流程里能借的原子

PRD 要的「表知识确认」区（粒度、主键、是否多维上卷、必须过滤条件、数据边界、使用指南）和「高频查询模板」素材，**轻量流程都不产出**，只有完整流程 `tableKnowledgeGen` 有：

| ⑧ grainExplore | 粒度/主键 | 表知识确认 |

| ⑫ tableMetricDimLlm | 本表可算的指标、维度清单 | 候选知识点的参考 |

另一个差异：完整流程落私域（BPMN 里硬编码 `privately-owned`），轻量流程落公域。智能模式落公域。
