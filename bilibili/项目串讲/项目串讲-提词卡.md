# 工作部分提词卡（约 18 分钟）

> 对应 [[项目串讲]] 第三、四、五节。原则：**每段只讲一个结论，数字只留最有冲击力的 2–3 个，其余放 Q&A。**

## 0. 衔接（30 秒）

> "前面讲了 Atlas 在全景里的位置。我这半个月的工作落在一个很具体的问题上：**知识怎么被写进来、写得对不对。**
> 两个项目：项目一管'调用可不可观测'，项目二管'知识迁得对不对'。"

## 1. 项目一：MCP 工具调用埋点与运营看板（9 分钟）

### 1.1 背景（1 分钟）

- Atlas 的知识写入/查询通过 MCP 暴露给 Agent，4 个 tool 对应 4 个后端端点。
- 问题是：**每天被谁调、调哪个、成功没有、慢在哪、为什么失败，没人说得清。**
- 现成三套机制都不够：
  - `OperationLogAspect`：入参 4096 字符截断，badcase 拿不到完整请求；
  - `@OperationLog` 落库：只覆盖资产侧，抛异常就不落；
  - `KnowledgeAuditPublisher`：事务 afterCommit 才发，失败调用记不到。

> 一句话：**要每次调用打一行结构化日志，落到 Hive，喂给看板和周报。**

### 1.2 链路（30 秒）

```
MCP 调用 → 切面打一行 JSON → 日志平台 → iceberg → Hive
        → Narya 看板（量/成功率/耗时）
        → 周报（失败明细 + LLM 归因）
```

### 1.3 三个真正的坑（4 分钟，重点）

**坑 1：日志平台单条上限 32 KB，超过不是截断，是整行丢弃。**

- 一开始我以为"丢一点无所谓"，实际是整行消失：`is_success`、`cost_ms`、`entities_cnt` 一起没。
- 例子：一次 `/ingest` 提交 30 个实体，入参约 40 KB，整行约 45 KB，被平台丢掉——**这次调用同时从调用量、成功率、耗时三个指标里消失。**
- 更糟：大批量导入恰恰最容易失败、也最慢，被丢的正好是最该统计的那批。

**坑 2：`/validate` 失败不抛异常，HTTP 还是 200。**

- 只在响应体里写 `passed=false`。
- 切面如果只 catch 异常，会把校验失败记成成功，看板上 validate 成功率永远 100%——而失败样本正是周报最需要的。

**坑 3：鉴权和埋点两个切面的顺序。**

- 埋点在外层：能记到 401，但拿不到 operator；
- 埋点在内层：operator 一定有值，但 401 记不到。
- 首期只上报鉴权通过的调用，401 进 v2；同时显式声明 `@Order`：鉴权 100，埋点 200。

> 空值语义一句话带过：14 个键每行都有，字符串空写 `""`、数值空写 `0`，整行不出现 null；但**同一个 0 在不同 tool 下含义不同**，算平均写入实体数必须先过滤 tool。

### 1.4 实现（2 分钟）

- `@McpToolLog` 注解 + `McpToolCallLogAspect`，`@Around("@annotation(...)")`；不用按类切，避免把 `handleValidation` 也拦进来；埋点自身异常只打 warn。
- 14 键契约，顺序固定，后续只追加。
- 截断 v2：从"行级预算"改成"分字段预算"：
  - 前 12 个统计字段不截；
  - `error_msg` 2 KB 独立预算；
  - `request_body` 16 KB / `response_body` 24 KB，只在两者同时超限时互相让配额，优先削更大的。
- 结构上不按字节硬切：解析 JSON → 反复砍最大数组/最长字符串 → 仍是合法 JSON，头部写 `_truncated` 摘要；实在放不下才退回字节前缀。

### 1.5 结果与反思（1.5 分钟）

- pre：43/43 行前缀正确、14 键齐全、可解析、无 null、trace_id 不重复；8 行截断后整行恰好 30,720 B，仍被完整采集。
- 线上两天 2,764 次调用，暴露了 v1 的问题：
  - 716 行截断（25.9%）；
  - 196 行 response 整段变占位；
  - 47 行 `error_msg` 被挤掉，覆盖 31% 的失败调用。
- v2 实测：22 KB 请求 + 103 KB 响应 → 整行 24,994 B，`error_msg` 2,048 B 完整保留。
- 【待补】看板最终数字：总调用量 / 成功率 / P99 / Top 失败规则（没有就用"以看板为准"带过）。

> 收口：**这件事难的不是打日志，是定字段契约**——字段顺序、空值语义、截断策略、下游怎么用。定错一次，看板 SQL 全部返工。

## 2. 项目二：增长域表知识导入与智能生成验证（9 分钟）

### 2.1 背景（1 分钟）

- 增长域 100+ 张私域表，知识已经在 `privately-owned`；业务希望转成 `growth` 公域，让 Narya 能消费。
- 约束是 ingest 规则 **D-11a：表知识全域唯一，私域除外**，判重键「表名 | 目标域」。
  - 同一张表可以同时在私域和多个公域；
  - 但某个公域落库后，其它公域再落同名表会被拦；
  - 所以必须逐表查重，不能整批提交。
- 清单 147 张：开始 97 张已上线、50 张未上线。

### 2.2 方法（30 秒）

每张表固定走一遍：

```
实时 schema → 目标域 lookup → 脚本生成 + 本地审计
→ validate（零写入）→ import（全批原子）→ 按 atomId 回读
```

### 2.3 三个真正的坑（4 分钟，重点）

**坑 1：私域 SP 不能直接搬。**

- 私域 SQL 模板大量引用私域表，公域消费者看不到。
- 处理：私域 SP 全部丢弃，按本表高频查询重建；多表 SQL 的 FROM/JOIN 依赖补齐；跨域 DT 的 bizId 必须实查，猜错就是 D-11a / D-13。

**坑 2：字段级指标和表级指标同义时，不能靠改名"消歧"。**

- 第 1 张表 35 个字段级 `_fv` MET，27 个与表级 MET 完全同义（去掉括号后 cname 逐字一致）。
- 当时的错误做法：给字段级加「（字段值）」后缀 → 造出 27 个重复实体，还把实现说明写进业务名。
- 正确做法：**同义 concept 直接复用表级 MET，不另建实体。** 后来逻辑删除 27 个重复 MET，字段改绑表级，44 条 BIND_MEANING 回读正确。

**坑 3：分批导入不是全事务，写前快照会过期。**

- Skill 为了处理 BIND_MEANING 对新建目标的依赖，拆成 round1 / round2；跨批没有自动回滚。第二轮命中 A-16 中断时，77 个实体已经落库；失败后不能拿旧 CREATE 载荷重跑，必须重查存量、改成更新再续跑。
- 同时，Skill 用 25 天前的 `propmeta_snapshot.json` 判断可写属性，结果 DT 的 `dimensions/metrics/summary`、FIELD 的 `knowledge_source` 被放行 → 两次 A-16。
- 结论：**写前约束必须读实时 schema，不能依赖离线快照。**

> 备用（被问到再讲）：1003 项语义复核一开始自造 `CONTRACT_FIRST` 判据，把正常的 `expression/aggregation` 误判成"定义不中立"，整类报了 232 项；复核后作废。真实问题是 128 项源知识证据不足。

### 2.4 结果（2 分钟）

- 原 50 张未上线表全部处理完，49 张唯一表已在 growth 落库。
- 94 个暂缓项有去向：写入 5、复用 13、跳过 74、依赖阻塞 2。
- 1003 项语义复核：名称调整 416（实际改名 371）、复用候选 418、源证据不足 128、此前已处理 41。
- 第 1 张表：94 个实体、100 条关系，按 atomId 回读 94/94 命中、100/100 命中，0 孤儿绑定。

### 2.5 反思（1.5 分钟）

- **`validate` 通过 ≠ 业务正确。** 它只能证明结构和依赖没问题，证明不了这个指标建得对不对、这个 SP 是不是真的独立产出这个指标。
- 复用上宁可缺、不滥建：`dau` 没有复用 `growth_met_dau`，因为后者是多屏 TV 口径，本表是财报口径；证据不足的就新建，但名称里不带实现说明。

## 3. 收获与后续（2 分钟）

### 收获（各一句）

1. **对业务链路的理解从"知道模块"变成"知道约束"**：D-11a 全域唯一、A-16 可写属性、D-13 的 N:1、cube 的重复计数——约束决定方案，不是写完再补校验。
2. **端到端验证比单点通过更重要**：单测和 pre 日志都过了，真正的风险是"整行被日志平台丢掉""error_msg 被截断""validate 过了但语义是错的"。
3. **口径先定、文档留痕**：14 个字段的顺序、空值语义、截断策略，每个都记录原因和取舍；每张表保留载荷、校验、回执、回读日志。

### 下一步（三条）

- 看板：补齐最终指标口径核对；周报按周自动出 badcase 归因。
- 增长域：第 2 张 `ads_boss_growth_mau_1m_d` 继续，一次一张。
- 质量门禁：8 条 Skill 缺陷 → 写前读实时 schema、同义指标强制复用、每字段必须有 BIND / SKIP / ROLE_FIX。

## 4. 高频追问（按需展开，不主动讲）

**Q1：为什么不用现成的链路追踪/日志？**
`OperationLogAspect` 4096 截断；`@OperationLog` 失败不落；Audit 在 afterCommit 才发。三套都拿不到"失败调用的完整证据"。

**Q2：为什么 401 首期不上报？**
埋点排在鉴权内层，才能保证每行 operator 有值；排外层能记 401 但 operator 为空。首期优先保证统计口径可用，401 进 v2。

**Q3：为什么不做采样？**
badcase 要的是失败样本，采样最容易丢的恰恰是低频失败；而且平台是整行丢弃，采样解决不了单行超限。

**Q4：为什么 D-11a 要逐表查重？**
判重键是「表名 | 目标域」，同一张表在其它公域落过就会被拦；整批提交一旦中途失败，跨批不回滚，清理成本更高。

**Q5：validate 都过了，为什么还要人工/LLM 复核？**
validate 只校验结构、依赖、属性白名单；业务语义（指标是否同义、SP 是否独立产出、口径是否一致）它证明不了。

**Q6：怎么保证迁移的知识是对的？**
每张表按 atomId 回读实体和关系；保留载荷、校验回执、回读日志；复用必须有证据，找不到证据就新建，宁缺毋滥。

**Q7：增长域批量 ACTIVE 是你做的吗？**
不是。那是别人通过 WEB 批量复核并 `scope=all` 发布的。本轮新知识一律保持 INACTIVE，发布或改 ACTIVE 必须另行授权。

**Q8：这个项目对团队的价值？**
项目一给知识写入做了可观测，能持续发现 badcase；项目二沉淀了一套可复用的导入与证据规范，下一批表可以直接照做。
