## 一、先记住一张图

```
                     ┌─────────────────────────────────────────┐
   数据生产/存储      │  BSK（Berserker）                        │
   事实发生的地方      │  开发 / 集成 / 调度 / 查询 / 质量 / 治理  │
                     │  知道：表长什么样、谁产出、血缘、权限      │
                     └───────────────┬─────────────────────────┘
                                     │ 元数据 + 生产 SQL + 消费 SQL
                                     ▼
                     ┌─────────────────────────────────────────┐
   数据语义层         │  Atlas（对外产品名 Ulduar）               │
   AI 能不能看懂      │  业务过程/实体/指标/维度/枚举/术语/规则/  │
                     │  问答/SQL 模板 —— 结构化原子 + 引用成图    │
                     └───────┬─────────────────────┬───────────┘
                             │ MCP / 点查           │ 连接器
                             ▼                     ▼
        ┌────────────────────────────┐   ┌────────────────────────────┐
        │ Narya —— 替你查数           │   │ Lumina —— 替你干活          │
        │ ChatBI：自然语言 → SQL/洞察 │   │ Agent 平台：建任务/改表/刷数│
        └────────────────────────────┘   └────────────────────────────┘
```

**一句话**：BSK 让数据"存在且可生产"，Atlas 让数据"能被 AI 理解"，Narya 和 Lumina 是 AI 消费数据的两个出口——一个查数，一个动手。

## 二、数据平台部是干什么的

**定位**（Info 部门主页原话）：

- 使命："业务数据化，数据业务化，让数据成为第一生产力"
- 提供"高效、自动、标准的数据集成、分布式存储、分布式计算及可视化的数据解决方案"

**两条腿**：

| 线条 | 内容 | 代表 |
|---|---|---|
| 数据建设（数仓） | 按业务线建模型、出指标、保 SLA | 数仓业务组：增长、直播、OTT、课堂等各业务线 BP |
| 平台工具（数平） | 把数据生产和消费做成产品 | BSK、数据地图、治理中心、北极星、Narya、Atlas、Lumina |

> ⚠️ Info 部门主页的团队名单看起来偏旧（仍是数仓平台/平台工具那套分工）。介绍组织时建议只讲"数仓 + 平台工具"两条线，具体人名以最新组织架构为准。

**为什么部门里既有数仓又有平台**：数仓是"数据本身"，平台是"让全公司能生产和消费数据"的工具。BSK 是平台侧的总入口，Narya / Atlas / Lumina 是平台侧在 AI 时代的延伸。

## 三、BSK：整个体系的地基

### 1. 它是什么

BSK = **Berserker**（内部简称 BSK，域名 `berserker.bilibili.co`），B 站的大数据开发治理平台。名字出自 Fate 的"狂战士"职阶。

官方定义（新手任务指南）：

> "不是简单把大数据生态组件拼接，也不是狭义的代码开发工具，而是在大数据生态组件之上，提供海量数据的传输、存储、查询分析、开发测试发布、管理、运维的一站式开发分析治理平台。"

### 2. 为什么存在

大数据生态早期，Hive、Spark、Flink、Kafka、调度、权限、质量各自独立，一个需求要在 N 个平台之间跳。BSK 的价值是把**同一条数据链路**收进一个门户：

| 环节 | BSK 模块 |
|---|---|
| 数据进得来 | 数据集成（MySQL/Taishan/Databus → Hive，反向出仓） |
| 存得下 | 数据管理、表/库管理、生命周期、冷存储 |
| 算得出 | 数据开发（SparkSQL/FlinkSQL/Shell/Python）、调度、基线 SLA |
| 查得到 | 数据查询 Adhoc（Presto/Spark）、数据地图、血缘 |
| 管得住 | 数据质量 DQC、治理中心、权限与安全等级、成本账单 |
| 看得见 | 数据建模、数据标准、指标服务、观星台/万华镜/北极星等应用 |

> BSK 门户范围还包括观星台、万华镜、指标服务、北极星、摩天楼等子产品（外包准入文档明确列过），讲"BSK 是个门户/生态"时有据可依。

### 3. 它在 AI 时代的角色

BSK 是**事实源和执行面**：

- 所有表的元数据、血缘、生产 SQL、消费 SQL（Keeper）在这；
- 所有"写"的动作（建表、改任务、刷数、发布）最终落在 BSK；
- 权限、保障等级、SLA 也在这。

**边界**：BSK 知道"这张表由哪个 job 产出、字段是什么类型、下游是谁"，但不知道"这个字段业务上是什么意思、这个指标口径包含什么不包含什么"。这就是 Atlas 存在的理由。

## 四、Atlas（对外叫 Ulduar）：让 AI 看懂数据

### 1. 名字先澄清

- "Unlder" 在知了文档里实际写作 **Ulduar**（魔兽世界的副本名，和 Berserker 一样是代号风格）。
- 从多处文档交叉看：**Atlas 是项目/系统名（本仓库即 app/atlas），Ulduar 是对外产品名和域名**（`ulduar.bilibili.co`，pre 环境为 `pre-ulduar`）。Lumina 连接器文档直接写"Atlas（数据知识平台）"，另一处写连接器叫 `ulduar`（知识图谱），Agent 自述也是"Atlas/Ulduar 知识检索"。
- 串讲时建议统一说："**Atlas，对外叫 Ulduar 数据资产/知识平台**"。

### 2. 为什么存在（串讲的"题眼"）

猫耳接入 Narya 的方案文档把问题讲得最清楚：

> "光有表还不够——AI 看到一个字段，并不知道它的业务含义、单位，以及背后的口径规则（包含什么、不包含什么、怎么算）。"

拆成三个痛点：

1. **元数据 ≠ 知识**：BSK 有字段名和类型，但没有"这个字段是用户消费金额还是主播流水""金额单位是分还是元"。
2. **血缘 ≠ 口径**：知道表从哪来，不等于知道"总收入 = 个播 + 团播主麦 + 嘉宾，连麦不能重复累加"这种规则。
3. **文档 ≠ 机器可读**：业务知识散在知了、Info、人口口相传里，AI 检索到的是长文档片段，不是可直接引用的结构化事实。

行业侧的同一判断（Data Agent 圆桌）：

> "过去是人创建表、人理解表、人查询表，现在要求 AI 读表，语义必然丢失。"

Atlas 就是把这个"语义鸿沟"补上的那一层。

### 3. 它是什么：9 类知识原子 + 引用成图

Ulduar 平台支持 9 种知识点，分两类：

| 让人/AI 看懂数据 | 让 AI 答准业务 |
|---|---|
| 业务过程（BP） | 业务术语 |
| 业务实体（BE） | 业务规则（BR） |
| 指标（MET） | 常见问答（FAQ） |
| 维度（DIM） | SQL 模式/模板（SP） |
| 枚举值（ENUM） | |
| 属性（ATTR）、数据表（DT） | |

**知识是"原子 + 引用"的形式**，不是文章。猫耳直播域的实际数据可作例子：

```
业务过程(BP) ◄─挂靠─ 指标(MET) ──► SQL模板(SP) ──► 数据表(DT)
业务实体(BE)
        └── 属性(ATTR) / 枚举(ENUM)
```

猫耳域已录入：业务过程 6 · 业务实体 8 · 属性 100 · 指标 57 · 表 12 · 枚举 7 · SQL 模板 12 · 业务规则 5。

原子之间用 ID 互相引用（`bp_maoer_reward`、`met_maoer_live_listen_dau`、`br_maoer_amount_caliber`），织成知识图谱。所以 Atlas 不是"向量库 + 文档切片"，而是**可遍历、可引用、可校验的语义网络**——这是它相对 RAG 的核心差异。

### 4. 知识从哪来

四条路：

1. **人工/业务方录入**：业务域负责人把指标口径、业务规则录进 Ulduar。
2. **表知识自动生成**：Atlas 的 tableKnowledgeGen 流水线，从 BSK Keeper 拉元数据 + 生产 SQL，再跑数据探查 + LLM，自动产出一张表的完整知识（见第八节）。
3. **文档/知识导入**：dw-kb、Git 仓库、知了文档结构化导入。
4. **SQL/血缘挖掘**：从生产 SQL、消费 SQL 反推字段口径和用法。

### 5. 和 BSK、知了的边界

| | BSK | Atlas / Ulduar | 知了（aistudio） |
|---|---|---|---|
| 管什么 | 数据生产、元数据、调度、权限 | 数据的**业务语义与口径** | 研发**文档**知识 |
| 典型问题 | 这张表谁产出？跑成功了吗？ | 这个指标怎么算？这个字段能当维度吗？ | 这个方案怎么设计的？ |
| 消费方式 | 控制台 / Adhoc / MCP | MCP / Narya 点查 / API | 人读 / MCP / 知识库检索 |
| 归属 | 数据平台部 | 数据平台部 | 主站技术中心 |

**一句话**：BSK 管"数据的事实"，Atlas 管"数据的含义"，知了管"人的文档"。

### 6. 对外消费方式

- **MCP**：`ulduar.bilibili.co/connect`。数平官方建议"分析场景用 Ulduar MCP，生产场景用 BSK MCP"（时效性不同：知识库可接受分钟级延迟，生产以 BSK 为准）。
- **Narya 点查**：表详情、字段关系、指标口径。
- **Lumina 连接器**：预置好，零配置可用。

## 五、Narya：替你查数

### 1. 为什么存在

业务方要一个数，传统路径是：提需求 → 排队 → 数仓开发写 SQL → 出报表，周期以天计；或者自己学 Hive/SQL/表结构。Narya 把入口降到"用自然语言问"。

一句话定位：

> **巴小卡 = 替你动手；Narya = 替你查数。**

### 2. 它怎么工作

用户问："最近 7 天各业务线的直播 DAU 环比怎么样？"

1. 识别意图 → 落到某个**分析主题**（如「直播」）或首页通用入口；
2. 主题内挂的 **Skill** 和**知识库**给出业务域、可用表、指标口径；
3. 生成 SQL → 在 Presto/Spark 上跑；
4. 产出口径说明 + 图表 + 可导出知了/企微，也可配订阅定时推送。

数据来源自述包括：Hive/Iceberg、知识库、ETL 血缘、Titan（画像）、观远、TAPD。

### 3. 为什么它离不开 Atlas

猫耳方案的链路：

```
① DMS 导数 → ② BSK 落库 → ③ 构建知识库（让 AI 看懂 + 答得准） → ④ 对接 Narya
```

- 表落 BSK 后，Narya 能"看到"表结构和字段——**但看不到业务语义**；
- 经中转库导入的表，连血缘和生产逻辑都看不到；
- 所以要用 Atlas 把"人工沉淀的语义与口径"补回去。**知识库与 Narya 的打通在 2026-08-17 上线。**

强依赖知识也有两面性：

- 弊：知识没建到的地方就是盲区，容易"无法应答"；
- 利：可查的表和口径被强约束，输出收敛、可控，准确性有保障。

### 4. 现状数据

从每日使用日报看：

- 日活约 1000 人上下、日问答 1.1–1.6 万；
- **首页占约 55% 问答量、75% 用户**；
- 其余 260+ 主题长尾，头部是直播、OTT、BI-游戏、用增、课堂等；
- 大量主题是"单人深度使用"。

> 这组数据同时说明：入口很强（首页），但垂类主题的分发和复用不足——可作为"下一步优化"的引子。

## 六、Lumina：替你干活

### 1. 为什么存在

数据开发/运维的动作（建任务、改 SQL、建表、刷数、诊断失败、配基线）高度重复且强依赖平台知识。Lumina 是**线上 Agent 构建与编排平台**，把这些动作交给 Agent。

### 2. 它是什么

官方"数据开发专家"开箱即用，能力覆盖：

- 数据开发：建/改 SparkSQL、FlinkSQL、Shell、Python、PySpark 任务，测试、发布、冻结
- 数据同步：MySQL/Taishan/Databus → Hive 入仓，Hive → MySQL 出仓
- 表管理：按规范建 Hive 表、加字段
- SQL 编写与慢查询优化
- 数据运维：刷数、补数据、级联回刷、实例诊断
- 数据源管理

平台概念：**专家（Agent）/ 专家团（多 Agent 工作流）/ 技能（Skill）/ 连接器（Connector）/ 项目 / 资料 / 定时任务**。

### 3. 与 BSK、Atlas 的关系

- **连接器预置**：Berserker（建任务、编辑表、查实例、管基线、DQC）+ Atlas（查表结构、检索数据资产知识、捋血缘），零配置直接用。
- Lumina 是"**执行面 Agent**"：调 BSK 去改东西，调 Atlas 去查知识。
- 对外可被其它系统调：A2A HTTP API（`/api/v2`）和 MCP（`/api/mcp`）。

### 4. 和 Narya 的分工

| | Narya | Lumina |
|---|---|---|
| 本质 | 查数与分析（读） | 开发与运维（写/执行） |
| 用户 | 业务方、分析师 | 数仓开发、数据工程师 |
| 输出 | SQL、图表、报告、订阅 | 任务、表、发布、刷数、诊断结论 |
| 对 BSK | 读表、跑查询 | 读写平台对象 |

> 平台盘点 PPT 把 Ulduar 和 Lumina 标成"在建中"，但 Lumina 已有正式介绍、连接器文档、A2A 接入文档和使用记录，实际是**可用/灰度推进中**。串讲前建议确认最新口径。

## 七、把四者串成三条"旅程"

**旅程 A：业务方要一个数**

1. 在 Narya 首页/主题里用自然语言提问；
2. Narya 调 Atlas（知识）确认指标口径、可用表；
3. 生成 SQL，在 BSK 的表上跑；
4. 返回数字 + 口径说明；满意就沉淀成 Skill/订阅。

**旅程 B：数仓开发要改一张表**

1. 在 Lumina 对"数据开发专家"说："给这张表加个字段并上线"；
2. Lumina 调 Atlas 查表结构、血缘、下游影响；
3. 调 BSK 建表/改任务/冒烟测试/发布；
4. 全过程的表知识由 Atlas 的生成流水线补充回知识库。

**旅程 C：外部 Agent 接入**

MCP：Ulduar 提供知识检索、BSK 提供元数据与执行、Lumina 提供 Agent 调用（A2A）。

> 讲到这里可以收一句：**生产、语义、消费是三种不同的时间尺度和权限边界**，硬塞进一个系统会互相拖累——这就是为什么是三个平台而不是一个。

## 八、Atlas 项目目前在做什么

来自本仓库 `docs/specs/` 与代码。

### 1. 主线：表知识自动生成（tableKnowledgeGen）

给定一张 Hive/Iceberg 表（`库.表`），自动完成：

**元数据采集 → 确定性抽取 → LLM 洞察 → 存量知识匹配 → 真实数据探查（画像/枚举/粒度/cube）→ LLM 语义增强 → 统一校验落库**

14 个原子串行，Flowable 编排，每原子独立事务：

| # | 原子 | 一句话 |
|---|---|---|
| ① | collectFromKeeper | 拉元数据/生产 SQL/消费 SQL/表手册 |
| ② | tableBaseExtract | 建 DT + FIELD 骨架 |
| ③ | etlInsight | 从生产 SQL 提血缘、字段口径、cube/粒度先验 |
| ④ | knowledgeMatch | 给字段绑定已有官方 MET/DIM |
| ⑤ | tableDataProfile | 基数/空值等画像 |
| ⑥ | explorePlanLlm | 决定后续探查哪些列 |
| ⑦ | enumExplore | 枚举值分布 |
| ⑧ | grainExplore | 主键/表粒度 |
| ⑨ | cubeExplore | 多维上卷表识别与维度组合 |
| ⑩ | usageGuideLlm | 推荐关联、高频查询、性能提示 |
| ⑪ | fieldEnrichLlm | 字段描述/角色/枚举含义 |
| ⑫ | tableMetricDimLlm | 本表可算的指标与维度清单 |
| ⑬ | tableSummaryLlm | 中文名、五段式描述、数据边界 |
| ⑭ | tableArchive | 走统一 ingest 落库 |

产出：DT/FIELD 实体 + 属性 + 关系（含 BIND_MEANING），供下游 Agent 选表、写 SQL、拦口径错误。

### 2. 覆盖与消费

- 存量侧：文档中出现 **33,334 张表 kb.md**（多屏团队知识地图把 Atlas 定义为"表级知识、AI 召回底座"）。
- 消费侧：Narya 点查、表知识 Markdown MCP（`read_table_knowledge`）、知识文档发布到知了、轻量表生成（lite）与批次调度。

### 3. 治理与质量

- 统一 ingest 入口：19 条校验规则、全批原子事务、删除级联、D-11/D-11a 全域唯一；
- 质量评测：覆盖度评测、Pipeline vs Narya 对比、247 表全量评测；
- 已知难点：
  - ads/聚合表的粒度（grain）与 cube 识别存在结构性失败；
  - DUP/REL 冲突检测的召回与精度；
  - 公域/私域知识隔离；
  - 自动生成 vs 人工权威录入的口径一致性。

### 4. 一句话路线

> **从"人工录入知识"走向"自动生成 + 人工校验 + 统一落库 + 多端消费"。**

## 十、容易被追问的 7 个问题

**Q1：Atlas 和 Ulduar 是两套东西吗？**
一套。Atlas 是项目/代码名，Ulduar 是对外产品名。Lumina 连接器里两个名字都出现过（"Atlas（数据知识平台）"、`ulduar` 知识图谱）。

**Q2：Atlas 和知了（aistudio）什么关系？会不会重复？**
不重复。知了是**文档**知识（方案、周报、复盘），给人读；Atlas 是**数据语义**知识（指标口径、字段含义、业务规则），给 AI 和取数平台用。两者有导入通道，但定位和消费方式不同。

**Q3：Narya 和 Lumina 都是 AI，为什么不做成一个？**
读和写是两种权限模型、两种风险。Narya 面向业务方做只读取数与分析，Lumina 面向开发做写操作（建表、发布、刷数），混在一起权限和审计都收不住。

**Q4：为什么 Atlas 要做成图谱/原子，直接上 RAG 不行吗？**
RAG 召回的是文档片段，适合"找资料"，不适合"算指标"。取数要求口径唯一、可引用、可校验、可追溯到表——所以需要原子的 ID 引用（指标→SQL 模板→表）和业务规则约束。猫耳的例子最直观：用户侧金额和主播侧流水"同过程、不同口径、不可对比"，这种硬约束只能写成结构化规则。

**Q5：BSK 为什么自己不做知识库？**
BSK 的职责是生产与治理；知识需要跨源（BSK 元数据 + SQL + 人工口径 + 文档）持续维护和评测，且要被多家 Agent 消费。做成独立一层更合理，也避免把知识演进绑在生产平台的发布节奏上。

**Q6：33,334 张表的知识质量怎么保证？**
三道：生成侧用真实数据探查（画像/枚举/粒度/cube）而不是只靠 LLM 读 SQL；落库侧走统一校验（19 条规则）；评测侧做覆盖度与 Pipeline vs Narya 对比。仍有已知短板，不要宣称"全自动高准确"。

**Q7：这些平台现在到底上线了没有？**
Narya 已上线并有稳定日活；Atlas/Ulduar 有生产域名和 MCP，处于铺开阶段；Lumina 已有正式入口和 A2A 接入。平台盘点 PPT 标"在建中"，讲之前按最新状态校准一次。
