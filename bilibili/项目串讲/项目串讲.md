# 二、业务理解

## 1. 我们组解决的是什么问题

运营、产品、UP 主运营、商业分析师每天都会问数据问题：

- 昨天这个活动的转化怎么样？
- 这个功能上线后 DAU 有没有变化？
- 这个 UP 主的粉丝为什么掉了？

问题不在"有没有数据"，而在**取数门槛**。业务同学要自己上 BSK 取数，得先选对表、懂分区、懂口径、会写 SQL。四道门槛里任何一道没过，取数就失败。

具体可以拆成三个痛点：

| 痛点 | 具体表现 | 后果 |
|---|---|---|
| 选表靠猜 | 平台上万张表，名字相似，不知道哪张才是自己要的 | 反复试错，或者问人 |
| 口径靠问 | 含不含退款、按下单时间还是支付时间，光看字段看不出来 | 只能找表 owner，沟通成本高 |
| SQL 容易写错 | 忘分区裁剪、对 cube 表直接 SUM 导致重复计数、时间窗口端点写错、JOIN 键要解析表达式却直接等值关联 | 数取出来了，但是错的 |

所以组里在做 Data Agent：**Narya** 面向业务问题找表、找知识、写 SQL；**Lumina** 更偏通用助手。而 **Atlas 是这些 Agent 的知识底座**——Agent 能不能答对，取决于 Atlas 里的表知识、指标口径、维度枚举、业务术语准不准、全不全。

## 2. Atlas 的三层结构

我理解 Atlas 可以拆成"生产 → 管理 → 消费"三层：

| 层 | 解决什么 | 核心机制 | 我这半个月的工作落点 |
|---|---|---|---|
| 知识生产 | 知识从哪里来 | 从 Keeper 采集元数据、从 Adhoc 做真实数据探查、从 Archer 取调度信息；域知识和表知识两条 Pipeline，表知识流程约 14 个原子 | 项目二：增长域表知识从私域迁移到公域 |
| 知识管理 | 知识怎么组织、怎么保证质量 | 本体模型（Entity / Relation / Property）；ingest 写入闸门（A-/B-/D- 三类规则）；DUP → ATTR → REL 三阶段冲突检测；审计与复核发布 | 项目二大量用到这套闸门 |
| 知识消费 | 知识怎么用出去 | MCP、HTTP API、对外快照/订阅、检索、转知了文档，供给 Narya、Lumina、AB Agent 和接个人 token 的 Agent | 项目一：给 MCP 调用本身做可观测 |

一句话概括：**Atlas = 一套本体 + 一套写入闸门 + 两条生产流水线 + 多个消费出口。**

### 本体模型长什么样

本体不是抽象概念，它决定了知识能怎么被表达和查询。按层次可以这样记：

| 层 | 类型 | 是什么 | 例子 |
|---|---|---|---|
| 业务语义 | BP 业务过程 | 一次可度量的业务动作 | 播放、投币、关注 |
| 业务语义 | BE 业务实体 | 业务对象/主体 | 用户、稿件、UP 主 |
| 逻辑模型 | MET 指标 | 可聚合的业务度量 | 播放量、投币率 |
| 逻辑模型 | DIM 维度 | 分析视角或描述特征 | 设备类型、日期、用户 ID |
| 逻辑模型 | ENUM 枚举值 | 维度的具体取值 | ios / android / web |
| 物理模型 | DT 数据表 | 一张物理表 | iceberg_bdp.dwb_usr_video_play_di |
| 物理模型 | FIELD 字段 | 表里的一列 | dwb_usr_video_play_di.play_cnt |
| 其他 | BT 业务术语 | 行业黑话解释 | "三连" = 点赞 + 投币 + 收藏 |
| 其他 | BR 业务规则 | 口径规则 | 播放量需去重 |
| 其他 | SP SQL 模版 | 可复用的完整查询 | 带参数的取数范式 |
| 其他 | FAQ 问答 | 常见问题及解法 | — |

**为什么要有本体**：如果知识只是 Word 和 JSON，关系找不到、口径不统一、没法复用。抽象成实体、关系、属性之后，知识才能被查询、被 Agent 消费，也才能用规则去做质量校验。

**为什么要有闸门**：知识写进来不等于写对了。比如同一张表在两个域各落一份、一个字段绑了两个指标、必填属性漏填——这些都要在写入时拦住。这就是我项目二里反复碰到 D-11a、D-13、A-16 的原因。

# 三、工作内容介绍

### 项目一：MCP 工具调用埋点与运营看板

#### 1. 项目背景

Atlas 的知识写入和查询通过 MCP 暴露给 Agent，主要有四个工具：写入知识、零写入预检、查存量、查 schema。

问题是：这些工具每天被谁调用、调的是哪个、成功没有、慢在哪、失败原因是什么，没有统一答案。

现有三套机制都不满足：

- 操作日志：入参在 4096 字符处截断，badcase 拿不到完整请求；
- 业务操作日志落库：覆盖范围有限，抛异常就不落；
- 知识审计快照：事务提交后才发送，失败调用记不到。

目标很明确：每次调用打一行结构化日志，经日志平台落到 Hive，再供给两个出口——Narya 指标看板和每周的 badcase 分析报告。

```
MCP 调用 → 结构化日志 → 日志平台 → Hive → 看板 / 周报
```

#### 2. 关键问题与取舍

**第一，日志平台单条上限 32 KB，超过不是截断，是整行丢弃。**

- 原以为"丢一点无所谓"，实际是整行消失，成功率、耗时、实体数等统计字段一起没；
- 一次提交 30 个实体，整行约 45 KB，被平台丢掉，这次调用同时从三个指标里消失；
- 大批量导入恰恰最容易失败、也最慢，被丢的正好是最该统计的那批；
- 结论：必须在应用侧把整行控制在 30 KB 以内。

**第二，不同工具的"失败"语义不一致。**

预检工具校验不通过时不抛异常，照常返回 200，只在响应体里写失败。如果只看有没有异常，会把校验失败记成成功，成功率永远 100%——而失败样本正是周报最需要的。

**第三，鉴权失败与埋点的顺序。**

埋点排在鉴权外层：能记到 401，但拿不到操作人；排在内层：操作人一定有值，但 401 记不到。首期选择只上报鉴权通过的调用，401 留到下一版；同时显式固定两个切面的顺序，避免依赖默认行为。

**第四，空值语义必须提前定。**

字符串没值写空串、数值没值写 0、整行不出现 null。带来的坑是同一个 0 在不同工具下含义不同（写入失败，或该工具根本不写库），下游算"平均每次写入实体数"时必须先按工具过滤。

#### 3. 我的做法

- 用注解声明工具名，切面统一埋点；不按控制器类切，避免把异常处理方法也拦进来；
- 埋点自身出错只打警告，不改变接口返回值或异常；
- 固定 14 个字段的契约，顺序不变，后续只往末尾追加；
- 截断从"整行预算"改为"分字段预算"：前 12 个统计字段不截；错误信息独立 2 KB；请求 16 KB、响应 24 KB，两者同时超限才互相让配额，优先削更大的；
- 结构上不再按字节硬切：解析 JSON 后反复收缩最大的数组或最长的字符串，保证结果仍是合法 JSON，并在头部记录截断摘要；实在放不下才退回字节前缀截断。

#### 4. 结果

- pre 验证：43 行全部字段齐全、顺序正确、可解析、无 null；8 行截断后整行恰好 30,720 B，仍被平台完整采集；
- 线上两天 2,764 次调用，暴露第一版截断策略的问题：716 行截断（25.9%）、196 行响应整段变占位、47 行错误信息被挤掉，覆盖 31% 的失败调用；
- 第二版实测 22 KB 请求 + 103 KB 响应：整行 24,994 B，错误信息 2,048 B 完整保留；
- 看板可按工具、操作人、域看调用量、成功率、耗时分布；badcase 周报基于失败行做归因；
- 【待补】看板最终数字：总调用量、整体成功率、P99 耗时、Top 失败规则。

这件事真正难的不是"打日志"，而是定字段契约——字段顺序、空值语义、截断策略、下游怎么用。定错一次，下游加工和看板 SQL 都要返工。

### 项目二：增长域表知识导入与智能生成验证

#### 1. 项目背景

增长域有 100+ 张私域表，知识已经沉淀在 `privately-owned` 私域域里；业务侧希望把这些知识转为 `growth` 公域知识，让 Narya 等 Agent 能正常消费。

Atlas 的约束是 ingest 规则 **D-11a：表知识全域唯一，私域除外**，判重键是「表名 | 目标域」。这意味着：

- 同一张表可以同时存在于私域和多个公域；
- 但一旦在某个公域落库，其它公域再落同名表就会被拦；
- 落库前必须逐表查重，不能整批提交。

同时还有一个次目标：验证"智能生成"技术——用 Skill + 脚本 + Agent 把私域知识迁移成公域知识，记录每一步用了什么提示词、结果如何、问题归因在哪。

原始清单 147 张表：开始时 97 张已上线，50 张未上线。

#### 2. 关键问题与取舍

**第一，私域 SQL 模板不能直接搬。**

私域里的模板大量引用私域表，公域消费者看不到。处理方式是：私域模板全部丢弃，按本表的高频查询重建；多表 SQL 的 FROM / JOIN 依赖要补齐；跨域表的 bizId 必须实查，不能猜——猜错就是 D-11a / D-13。

**第二，字段级指标与表级指标同义时，不能靠改名"消歧"。**

第 1 张表有 35 个字段级指标，其中 27 个与同表表级指标完全同义（去掉括号后中文名逐字一致）。当时的错误处理是给字段级指标加「（字段值）」后缀，结果制造了 27 个重复实体，还把实现说明写进了业务名。正确做法是：同义概念直接复用表级指标，不另建实体。后来把 27 个重复指标逻辑删除，字段改绑表级指标，44 条绑定关系全部回读正确。

**第三，分批导入不是全事务，写前约束不能依赖离线快照。**

Skill 为了处理绑定关系对新建目标的依赖，把导入拆成两轮；跨批没有自动回滚。第二轮被校验拦截时，77 个实体已经落库。失败后不能直接拿旧载荷重跑，必须重新查实时存量、把已落库对象改成更新，再续跑。

同时，写前白名单用的是一份 25 天前的离线快照，把内部维护属性放行了，连续两次被服务端校验拦住。结论：写前约束必须读实时 schema，不能依赖离线快照。

**第四，判据不能自造。**

1003 项语义复核一开始用了自造判据，把目标指标正常的表达式和聚合方式误判成"定义不中立"，整类报了 232 项。复核后作废：真实问题是 128 项源知识证据不足（缺留存窗口、成本单位、比率分母、去重规则等）。

#### 3. 我的做法

整体按"清单 → 逐表 → 回读"推进，每张表固定走一遍：

```
实时 schema → 目标域查存量 → 脚本生成 + 本地审计
→ 服务端零写入预检 → 全批原子导入 → 逐实体逐关系回读
```

几条原则：

- 私域模板丢弃，按高频查询重建；跨域依赖必须实查，不能猜；
- 同义指标复用存量，不另建实体；证据不足宁可不建，但名称里不带实现说明；
- 每张表保留载荷、校验、回执、回读日志；完成后把提示词、轮次、结果、问题、归因追加到总清单。

#### 4. 结果

- 原 50 张未上线表全部处理完，49 张唯一表已在 growth 落库；
- 94 个暂缓项有明确去向：写入 5、复用 13、跳过 74、依赖阻塞 2；
- 1003 项语义复核：名称调整 416（实际改名 371）、复用候选 418、源证据不足 128、此前已处理 41；
- 第 1 张表完成 94 个实体、100 条关系，逐条回读全部命中，并修掉 27 个重复指标；
- 8 条 Skill 缺陷已记录：能临时修的已经修了，需要机制解决的写进续跑说明。

`validate` 通过不等于业务正确。它只能证明结构和依赖没问题，证明不了指标建得对不对、模板是不是真的独立产出这个指标；业务语义必须逐条审核。

# 四、通过这两个项目的收获

1. **对业务链路的理解从"知道模块"变成"知道约束"。**
   Atlas 不是一个简单的 CRUD 系统，难点在约束：D-11a 的全域唯一、A-16 的可写属性、D-13 的 N:1、cube 表的重复计数、私域与公域的隔离。这些约束决定了方案能怎么做，而不是写完代码再补校验。

2. **端到端验证比单点通过更重要。**
   项目一里，单测通过、pre 日志能打出来，但真正的风险是"整行被日志平台丢掉"和"error_msg 被截断"——这两个都是上线看数据才暴露的。项目二里，validate 通过但业务语义可能是错的。验证要覆盖到下游消费方，而不是停在接口返回 200。

3. **口径先定，文档留痕。**
   埋点 14 个字段的顺序、空值语义、截断策略，每一个都单独讨论过、记录过原因和取舍。增长域每张表都保留载荷和回读证据。后面别人接手、或者自己隔一周再看，能快速定位"当时为什么这么定"。

4. **业务理解决定方案质量。**
   项目一如果不知道"大批量导入最容易失败"，就会把截断顺序定成先截 request；项目二如果不知道"字段级指标和表级指标可能同义"，就会造出 27 个重复实体。代码只是业务规则的投影，业务理解不到位，代码写得再漂亮也可能是在正确地解决错误的问题。

# 六、个人想法和建议

1. **把"写前 schema 校验"统一成硬门禁。**
   这次 A-16 在 DT 和 FIELD 上各踩了一次，根因都是用了过期快照。建议所有知识导入入口（Skill、脚本、人工）都强制先调 `admin_knowledge_schema`，不读本地快照；服务端返回的只读属性直接作为过滤依据。

2. **把"知识质量"做成机器检查，而不是靠每次人工 review。**
   本轮验证出的几条规则都很适合自动化：每个 metric/dimension 字段必须有 BIND、SKIP（带原因）或 ROLE_FIX；同义指标必须复用；参与 `COUNT(DISTINCT)` 的标识符不能建成 MET。建议沉淀成导入后审计脚本，跑完再让人看结论。

3. **让 MCP 埋点反哺知识生产。**
   看板现在解决的是"调用可观测"，下一步可以按失败 query 聚类：哪些域、哪些表、哪类问题一直有人问但知识没接住。这些高频失败样本可以直接排知识生产优先级，也能沉淀成评测集，不用每次从零翻日志。
