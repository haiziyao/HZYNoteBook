# 权限设计：九种模型手撕速记

权限模型不是规定你必须建几张表，而是在回答不同的权限问题。

先用一句人话区分它们：

| 模型 | 它最关心的问题 |
| --- | --- |
| ACL | 这个具体东西的名单里有谁？ |
| DAC | 这个东西的主人愿意授权给谁？ |
| MAC | 用户和资源的安全等级是否匹配？ |
| ABAC | 用户、资源和环境是否满足一组条件？ |
| RBAC | 用户担任什么角色，角色能做什么？ |
| TBAC | 用户当前是否在处理这个任务？ |
| T-RBAC | 用户既有合适角色，又在处理这个任务吗？ |
| OBAC | 用户和这个业务对象是什么关系，对象现在是什么状态？ |
| UCON | 使用开始后，条件是否仍然一直满足？ |

## 手撕 ACL

> 给每一个具体资源贴一张访问名单。

```text
用户 2 + 文档 1001 + UPDATE
= 用户 2 可以修改文档 1001
```

最简单的三张表：

```text
sys_user
document
document_acl(document_id, user_id, action)
```

```sql
SELECT 1
FROM document_acl
WHERE document_id = #{documentId}
  AND user_id = #{userId}
  AND action = #{action}
LIMIT 1;
```

查到就允许，查不到就拒绝。详细讲解：[ACL.md](./ACL.md)

## 手撕 DAC

> ACL 再加一个“资源所有者”，由所有者决定授权给谁。

```text
用户 1 是文档 1001 的主人
用户 1 把 READ 授给用户 2
```

核心数据：

```text
document(id, owner_id)
document_grant(document_id, grantor_id, grantee_id, action)
```

所有者天然允许；其他用户必须存在授权记录。详细讲解：[DAC.md](./DAC.md)

## 手撕 MAC

> 不看主人愿不愿意，只按系统规定的安全等级强制判断。

```text
用户等级 3，文件等级 2：可以读
用户等级 2，文件等级 3：不可以读
```

核心数据：

```text
sys_user.security_level
document.security_level
```

读取通常要求：`用户等级 >= 资源等级`。详细讲解：[MAC.md](./MAC.md)

## 手撕 ABAC

> 把权限写成一组 if 条件。

```text
如果用户部门 = 文档部门
并且用户等级 >= 文档要求等级
并且现在处于工作时间
那么允许 READ
```

属性放在用户、资源和请求环境中，SQL 或策略引擎负责判断条件。详细讲解：[ABAC.md](./ABAC.md)

## 手撕 RBAC

> 用户不直接拿权限，用户拿角色，角色再拿权限。

```text
张三 → 财务角色 → 报销审核权限
```

经典五张表：

```text
sys_user
sys_role
sys_permission（项目中也可以叫 sys_menu）
sys_user_role
sys_role_permission
```

详细讲解：[RBAC.md](./RBAC.md)

## 手撕 TBAC

> 用户因为正在处理某个任务，临时获得这个任务当前允许的操作。

```text
报销单 1001 处于财务审核
用户 2 是当前处理人
财务审核状态允许 PAY
→ 用户 2 可以付款
```

详细讲解：[TBAC.md](./TBAC.md)

## 手撕 T-RBAC

> TBAC 再加角色限制：既要是处理人，也要有合适角色。

```text
用户 2 是任务处理人
+ 用户 2 有财务角色
+ 当前状态允许财务角色 PAY
= 允许付款
```

详细讲解：[T-RBAC.md](./T-RBAC.md)

## 手撕 OBAC

> 根据用户与对象的业务关系，以及对象当前状态决定权限。

```text
用户 2 是订单 1001 的 BUYER
订单处于 PENDING_PAYMENT
BUYER 在该状态可以 CANCEL
→ 允许取消
```

详细讲解：[OBAC.md](./OBAC.md)

## 手撕 UCON

> 不只在开始时检查，使用过程中还要持续检查。

```text
开始播放时会员有效：允许
播放中会员过期或超过 30 分钟：立即停止
```

详细讲解：[UCON.md](./UCON.md)
