## 简历文案候选稿

### Atlas｜面向数据分析 Agent 的知识构建与治理平台

**技术栈：** Java、Spring Boot、MySQL、MyBatis-Plus、Redis、Redisson、Flowable、LLM、Trino。

**项目描述：** 面向企业数仓知识分散、业务口径不统一、人工维护成本高的问题，整合表元数据、生产消费 SQL 和业务文档，构建覆盖知识抽取、语义关联、数据验证、审核发布及检索消费的知识治理平台，为数据分析 Agent 提供选表与 SQL 生成依据。

**项目亮点：**

- **异步任务编排与分布式资源治理：** 针对知识构建依赖多个耗时外部服务、失败后重复执行成本高的问题，基于 **Flowable 将单表构建拆分为 14 个异步节点**，通过模板方法统一输入校验、异常分类和执行埋点，实现节点级重试与多 Pod 协同调度；结合 **Redisson 可过期信号量**，按环境、资源类型及调用标签控制集群并发，实现资源按需借还与异常租期回收。
- **批量导入性能优化：** 通过分阶段耗时埋点，拆解元数据采集、语义匹配和事务落库开销，定位并优化 Keeper 采集瓶颈；在 **10 表批量导入实验中，元数据采集累计耗时下降 93.4%，端到端耗时下降 49.6% 至 9.41 秒**；在包含 **1,149 个字段的 5 张大表实验中，总耗时下降 25.0% 至 39.62 秒**。
- **规则与大模型协同的知识构建：** 针对字段业务语义缺失、纯模型推断缺乏验证的问题，设计“**血缘继承／历史复用 → 精确匹配 → LLM 兜底**”的分层匹配机制，并通过候选范围和结果校验约束模型输出；针对大表粒度探查组合爆炸，引入“**LLM 候选提名 + SQL 唯一性验证 + 子集最小化**”机制，将语义推断与数据验证结合，减少盲目穷举。
- **批量写入一致性与知识冲突治理：** 面向实体、属性、关系的关联写入，构建“**结构校验 + 业务查库校验**”两阶段规则链，通过请求级查询缓存复用校验数据，并以事务保障批量写入原子性；针对重复实体、属性口径及关系冲突，建立分阶段检测机制，以 **Redis pair 级处理记忆**保留人工裁决，使新增候选可继续检测、已处理实体对保持有效。
- **图查询性能与数据隔离治理：** 针对关系展开引起的查询放大及私域数据越界问题，将域过滤下推至 SQL，建设按层批量加载、深度限制与访问集合防环的查询内核；统一域、发布状态及生产消费侧可见性规则，通过 **SQL 与 Java 判定对拍测试**约束列表、统计和详情口径一致。

## 后续需要补齐的面试准备

### 异步编排：优先验证是否撑得住追问

- 为什么需要 Flowable，为什么拆成 14 个节点，各节点的事务边界是什么？
- 单实例串行与多表并行如何实现，多 Pod 如何竞争和持有 Job？
- 重试如何区分业务失败与技术失败，外部调用成功但事务失败会怎样？
- 幂等具体落在哪些写入动作上，节点级恢复的边界是什么？
- Job 锁、信号量租期、外部调用超时如何配合？
- 配额等待是否阻塞工作线程，线程池、连接池和外部资源配额如何匹配？
- Pod 重启、死信、僵死实例、跨环境共享资源等故障如何处理？
- 有哪些已验证指标：单表耗时、批次吞吐、并发配置、失败率、恢复时间、P95/P99？缺少的数据需明确标记待补。

### 其他亮点的关键追问

- 性能：49.6% 的基线、样本、环境和测量口径是什么？具体优化发生在哪个服务？
- 知识构建：模型输出如何约束，错误候选如何拒绝，探查如何减少扫描成本？
- 一致性：批内引用、重复提交、并发写入、部分失败如何处理？事务与幂等分别保证什么？
- 冲突治理：pair 为什么比整组记忆合适，Redis 持久化和数据库修改如何协调？
- 查询：过滤下推、批量加载和递归边界分别解决什么问题，如何验证口径一致？
