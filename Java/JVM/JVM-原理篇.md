## 栈上的数据存储
Java 8大基本数据结构

#### 基本数据类型存储

| 数据类型分类  | 数据类型       | 堆内存占用（字节数） | 栈中 slot 数 | 虚拟机内部符号 |
| ------- | ---------- | ---------: | --------: | :-----: |
| 整型      | byte       |          1 |         1 |    B    |
| 整型      | short      |          2 |         1 |    S    |
| 整型      | int（默认）    |          4 |         1 |    I    |
| 整型      | long       |          8 |         2 |    J    |
| 浮点型（小数） | float      |          4 |         1 |    F    |
| 浮点型（小数） | double（默认） |          8 |         2 |    D    |
| 字符型     | char       |          2 |         1 |    C    |
| 布尔型     | boolean    |          1 |         1 |    Z    |

**boolean、byte、char、short在栈上是不是存在空间浪费？**

是的，Java虚拟机采用的是空间换时间方案，在栈上不存储具体的类型，只根据slot槽进行数据的处理，浪费了一些内存空间但是避免不同数据类型不同处理方式带来的时间开销。

同时，像long型在64位系统中占用2个slot，使用了16字节空间，但实际上在Hotspot虚拟机中，它的高8个字节没有使用，这样就满足了long型使用8个字节的需要。

#### boolean在栈上的存储方式

``` java
boolean a = true;
if(a){};
if(a == true){};
```

由于boolean在虚拟机是一个槽,int也是.
所以虚拟机实际在 .class文件中,就是把boolean改为一个 int 类型,
使用的都是int的字节码指令

>上面演示的代码实际上我们可以手动搞出一点问题
>比如说,我们对 .class文件进行更改,把 `iconst_1`指的是赋值a的值的时候
>我们改为`iconst_2`
>就会有上面成立,下面不成立
>原因在于底层字节码
>`if(a)` 实际是 把 a 和 0 做是否相等的判断
>而 `if(a == true)` 是 a 和 1做判断

`标记字段`
- 正常状态
	- 锁状态 (2)
	- 偏向锁 (1)
	- 分代年龄 (4)
	- Cms使用 (1)
	- HashCode (31)
	- 未使用 (25)

- 垃圾回收标记

> JDK 8 默认开启指针压缩,可能看到实际与上面的理论不同

`指针压缩`
把原来 8 个字节的指针 压缩为 4个字节的
使用指针压缩,需要进行 8 字节 内存对齐(但是hotspot自动开启内存对齐)
(指针压缩的寻址空间只有32GB)


`对象数据`
对象数据会做一个 8 字节的对齐
(这个对齐不是因为压缩指针)
对齐主要是为了解决并发情况下CPU缓存失效的问题,
在缓存行中, 是以8个字节为单位的
如果A和B在同一个缓存行,A更新了,A和B都会被删除,B的缓存也会失效

`字段重排列`
HotSpot要求 每个属性的Offset能被当前字段长度整除,
如果重排列还不行,就会内存对齐填充,然后对齐


## 方法调用的原理

`invokestatic`: 调用静态方法
`invokespecial`: private,构造,super父类方法,构造方法,实现接口的默认方法
`invokevirtual`: 非private
`invokeinterface`: 调用接口方法
`invokedynamic`: 调用lambda


### 静态绑定
编译期间，invoke指令会携带一个参数符号引用，引用到常量池中的方法定义。方法定义中包含了类名 + 方法名 + 返回值 + 参数。

在方法第一次调用时，这些符号引用就会被替换成内存地址的直接引用，这种方式称之为静态绑定。
- invokestatic
- invokespecial
- final修饰的invokevirtual

### 动态绑定
对于子类,可能会重写父类方法,那么就需要动态进行绑定来完成方法地址绑定的工作

invokevirtual使用了 虚方法表 vtable
invokeinterface 使用了 接口方法表 itable

Cat 继承 Animal, 会把Animal的所有方法地址Copy一下, 如果重写了某个方法,
就用新地址替换原地址


## 异常捕获的原理

维护了一个 异常表,  捕获到异常的如果能处理,就跳转,如果不能,方法栈帧直接弹出.


## JIT即时编译器

JIT优化热点代码,把字节码转为机器码

- C1: 编译效率快.适用于短小代码
- C2: 优化效果好, 适用于服务端
- Graal



### 分层编译
- 0级: 解释器,执行,记录方法调用次数和循环次数
- 1级: C1完整优化
- 2级: C1完整优化,记录调用次数和循环次数
- 3级: C1完整优化,记录所有额外信息
- 4级: C2完整优化

C1和C2都有自己的线程



### 优化手段
- 方法内联
	- 方法编译之后的字节码指令总大小 < 35字节，可以直接内联。（通过-XX:MaxInlineSize=值 控制）
- 逃逸分析
	- 逃逸分析指的是如果JIT发现在方法内创建的对象不会被外部引用，那么就可以采用锁消除、标量替换等方式进行优化。


可以使用JIT Watch去查看



## 垃圾回收器

### G1 GC
* 年轻代回收(Young GC)
* 混合回收(Mix GC)


回收原理--- 三色标记法
* 黑色: 当前对象在 GC Root引用链上, 同时他引用的其他对象 也都已经标记完成
* 灰色: 在GC Root 链上, 引用的对象还未完成标记
* 白色: 可回收


黑色和白色通过位图实现.
灰色是维护的一个队列

这套方法存在并发问题,如果G1在回收期间代码有并发执行, 那么会出现错标记问题.比如我们执行A.b = null, C.b = B的时候,在扫描到A的时候,B的内存会被标记为 白色(要被回收),此时如果 C在 A之前就已经被标记一次了,那么B 挂上去的时候不回再触发一轮新的标记,那么B就被回收了

所以 G1 使用 快照的方法进行解决: SATB 
- 标记开始时候 创建快照
- 采用前置写屏障, 如果该对象在快照中,引用链断开之后就加入到 该线程的 SATB队列
- 按照默认存活处理这些对象,同时处理他们的引用对象

转移:
- 根据最终标记的结果,可以计算出来每一个区域的垃圾对象占用内存大小, 根据停顿时间,选择转移效率最高的几个区域
- 转移时先转移 GC Root直接引用的对象, 然后再转移其他对象
- 回收老的区域,如果外部又其他区域对象引用了转移对象, 也需要重新设置引用关系

在G1垃圾回收器中，STW时间的主要来源是在转移阶段：

1、初始标记，STW，采用三色标记法标记从GC Root可直达的对象。 STW时间极短

2、并发标记，并发执行，对存活对象进行标记。

3、最终标记，STW，处理SATB相关的对象标记。 STW时间极短

4、清理，STW，如果区域中没有任何存活对象就直接清理。 STW时间极短5、转移，将存活对象复制到别的区域。 STW时间较长


### ZGC

- 初始标记: 标记直接引用对象, marked0 = 1 
- 并发标记: 并发标记,同时处理上个GC周期的重映射
- 标记结束: 整理工作
- 并发处理: 处理弱引用,软引用, 卸载类,清空XPage,回收映射表
- 转移开始: 转移GC Root直接关联的对象
- 并发转移: 转移,重映射

### ShenandoahGC
1、ShenandoahGC的区域定义与G1是一样的。

2、没有着色指针，通过修改对象头的设计来完成并发转移过程的实现。

3、ShenandoahGC有两个版本，1.0版本存在于JDK8和JDK11中，后续的JDK版本中均使用2.0版本。
