## 二、题目与答案

### 1. 请做一下自我介绍

### 参考回答

建议控制在 60～90 秒，结构如下：

1. **基本背景**：学校、专业、求职方向。
2. **最相关经历**：重点讲 Agent、LLM 应用或后端工程经历。
3. **技术能力**：只提与岗位相关且能经得住追问的内容。
4. **成果与匹配度**：用真实指标说明效果，最后说明为什么适合这个岗位。

示例：

> 面试官您好，我是……，目前主要关注 Agent 应用和后端系统开发。我在上一段实习中参与了一个分析类 Agent，主要负责工作流编排、工具接入和结果校验。系统会把用户任务拆解为若干步骤，调用检索、数据查询和分析工具，再输出结构化结论。我重点解决过……问题，通过……把任务成功率从 A 提升到 B，平均耗时降低了 C%。此外，我还做过……项目，对 Python、异步任务、LLM Tool Calling、状态管理和可观测性比较熟悉。我希望继续做真实业务中的 Agent 工程化，因此应聘这个岗位。

不要虚构指标。如果没有线上数据，可以使用“测试集通过率、人工评审得分、P95 延迟、平均工具调用次数、单任务成本”等离线指标。

### 2. 你为什么会在实习期间经历两个部门？

### 回答思路

面试官主要想确认：部门变动是否由绩效或合作问题导致，以及你能否适应变化。回答应真实、正向，并把重点放在变动原因、工作连续性和收获上。

### 参考回答

> 当时是因为组织调整／项目阶段变化／业务需要，我从 A 部门转到 B 部门，并不是绩效原因。在 A 部门我主要负责……，完成到……阶段后，B 部门正好需要有……经验的人继续推进……，所以进行了调整。切换后我先梳理接口、文档和上下游依赖，再和两边负责人确认边界，保证了交接和项目连续性。这段经历让我更熟悉了……，也提升了跨团队沟通和快速理解业务的能力。

可能的追问：谁提出的转岗、两个部门各自的职责、交接怎么做、最终产出是什么。答案必须彼此一致。

### 3. 实习中是否真实经历过 Agent 内部流程编排？

### 参考回答

如果确实做过，可以按一次任务的生命周期回答：

> 我参与过。我们的编排不是简单地把用户输入直接交给模型，而是分为任务解析、计划生成、工具路由、执行、结果校验和答案合成几个阶段。请求进入后先生成 `run_id` 并加载会话状态；规划器把目标拆成带依赖关系的步骤；调度器根据工具描述、权限和当前状态选择工具；执行结果以结构化事件写回状态；校验节点检查 Schema、数据范围和引用依据，不通过时进行有限次数的重试或重新规划；最后由生成节点基于已经验证的证据组织答案。我的具体职责是……，主要解决了……。

还应主动说明：

- 编排是固定 Workflow、动态规划，还是二者结合。
- 状态存在哪里，如何恢复和重试。
- 工具失败、超时、重复执行和部分成功如何处理。
- 你修改过哪些代码，而不只是“使用了某个框架”。

如果没有直接做过，不要冒充做过：

> 我没有负责完整编排，主要负责其中的……模块，但我了解它在完整链路中的位置。完整流程是……；如果让我实现，我会……。

## 4～7. 实习相关具体细节追问（原帖未给出原题）

以下是常见追问框架，不属于原帖原题。

### 4. 你在项目中的职责边界是什么？

> 先用一句话描述团队目标，再区分“团队完成的内容”和“我亲自完成的内容”。说明自己负责的模块、关键提交、合作对象以及交付结果。不要把团队成果全部说成个人成果。

### 5. 项目中最难的问题是什么？

采用 STAR 结构：

- **S（背景）**：什么业务场景出现了问题。
- **T（任务）**：你需要达到什么目标。
- **A（行动）**：如何定位、有哪些候选方案、为什么选择当前方案。
- **R（结果）**：用真实指标或可验证现象说明改善。

### 6. 如何评估 Agent 的效果？

可以分层回答：

- 任务层：任务完成率、正确率、人工评审通过率。
- 过程层：规划成功率、工具选择准确率、工具调用成功率、重试率。
- 质量层：事实一致性、引用准确性、结构化输出合法率。
- 工程层：P50/P95 延迟、Token 消耗、单任务成本、异常率。
- 业务层：用户采纳率、节省时间、后续操作转化率。

### 7. 如果重做一次，你会改进什么？

> 不要回答“没有什么可改进”。可以从评测集、状态持久化、异常恢复、权限治理、可观测性或成本控制中选择一个真实薄弱点，说明当时为什么没做、现在会如何设计以及预期收益。

### 8. 分析师 Agent 返回的结论怎么确保正确？

### 核心观点

无法保证生成式模型 100% 正确，只能通过“证据约束 + 确定性校验 + 评测监控 + 必要时人工复核”把错误率控制在可接受范围内。

### 参考回答

> 我会把正确性拆成数据正确、推理过程可验证和最终表达一致三个层次。首先，限制 Agent 只能基于可信数据源作答，并保留每条结论对应的来源、查询条件和中间结果；其次，工具返回必须经过 Schema、类型、范围、时间窗口和业务规则校验，数值计算尽量由代码或 SQL 完成，而不是让模型心算；再次，让生成节点只能消费已经验证的证据，对关键结论做交叉来源核验或规则复算。低置信度、证据冲突和高风险结论进入人工复核。离线通过固定评测集统计任务正确率、事实一致性和引用准确率，线上进行抽样评审、异常监控和版本回归。

进一步可补充：

- 使用 `evidence_id` 将结论与证据绑定，避免“有引用但引用不支持结论”。
- 对 SQL、金额、比例等结果做确定性复算。
- 让校验器和生成器职责分离，但不能把“另一个 LLM 说正确”当作唯一依据。
- 设定最大重试次数；仍不确定时明确回答“不确定”，而不是继续幻觉。

### 9. 结构化结论使用什么格式？

### 参考回答

> 我们使用 JSON 作为模型与编排层之间的交换格式，并通过 JSON Schema 或 Pydantic 做强校验。相比自然语言，结构化格式方便路由、持久化、重试、前端渲染和自动评测。字段中除了结论，还应包含证据、置信度、状态和错误信息。模型输出校验失败时先进行有限次数的修复，仍失败则进入降级流程，不能把非法数据直接传给下游。

示例：

```json
{
  "status": "success",
  "summary": "核心结论",
  "findings": [
    {
      "claim": "结论 A",
      "evidence_ids": ["ev_001", "ev_003"],
      "confidence": 0.86
    }
  ],
  "warnings": []
}
```

注意：`confidence` 如果只是模型自报分数，不能直接视为真实概率，最好通过验证集进行校准，或把它改为基于规则的风险等级。

### 10. 介绍实习 Agent 的整体架构

### 参考回答框架

可以自上而下分为七层：

1. **接入层**：Web/API、鉴权、限流、会话入口。
2. **任务层**：意图识别、任务标准化、`run_id` 创建、优先级和超时预算。
3. **编排层**：规划、路由、状态机、重试、检查点和终止条件。
4. **能力层**：模型网关、RAG、工具注册中心、MCP/函数调用、代码或数据分析能力。
5. **状态层**：短期上下文、任务状态、长期记忆、证据和中间产物。
6. **治理层**：权限校验、输入输出校验、沙箱、高风险操作审批、成本控制。
7. **可观测层**：Trace、日志、指标、Token/成本、工具调用链和评测反馈。

### 示例表述

> 用户请求先经过接入层完成身份验证和限流，然后任务服务创建运行实例。编排器读取当前状态，由规划器生成步骤，再由路由器选择工具。工具调用并不是模型直接执行，而是经过统一 Tool Gateway 做参数校验、权限检查、超时和审计。执行结果写入状态存储并形成证据，校验节点决定继续、重试、重新规划还是终止。最终生成节点只基于通过校验的结果组织答案。整条链路通过 `trace_id/run_id/step_id` 串联，便于回放和定位问题。

回答时应结合自己的真实架构删改，避免把不存在的组件说进项目。

### 11. 介绍 Agent 从输入到返回结果的完整流程

### 参考回答

1. 接收用户输入，完成鉴权、限流、敏感内容检查和输入标准化。
2. 创建 `session_id/run_id`，加载该会话允许访问的上下文和能力。
3. 识别意图，判断是否可以直接回答，还是需要规划和工具调用。
4. 生成带依赖、预算和终止条件的执行计划。
5. 调度可执行步骤；并行步骤受并发数、资源配额和依赖关系约束。
6. 每次调用工具前，执行权限、参数和风险检查；调用后校验返回值并记录审计事件。
7. 把中间结果和证据写入当前运行状态，必要时进行有限重试或重新规划。
8. 达到终止条件后，基于证据生成结构化结论。
9. 对最终结果做 Schema、事实、敏感信息和引用检查。
10. 返回答案，同时异步记录指标和评测样本；中断的任务可从检查点恢复。

建议补充一个真实失败分支，例如：“工具超时后先指数退避重试两次；仍失败则切换备选数据源或返回部分结果，并明确标注缺失项。”

### 12. 为什么使用 OpenManus？

### 参考回答

> 当时项目处在原型验证阶段，需要快速搭建一个能规划、调用工具并执行多步任务的通用 Agent。OpenManus 是开源项目，代码相对直接，便于理解和修改 Agent 循环、Prompt、工具定义以及执行流程，也已经提供通用 Agent、工具扩展和浏览器/MCP 等能力，因此能降低从零搭建的成本。我们选择它不是因为它在所有维度都最好，而是它与当时“快速验证 + 深度定制”的目标匹配。

然后主动说明取舍：

> 它更适合作为原型和参考实现。生产化仍需要补齐持久化、任务队列、细粒度权限、可观测性、评测、幂等和故障恢复等能力。官方 README 也把 `run_flow` 多 Agent 版本标为不稳定，因此我们不会把实验能力未经治理直接用于关键业务。

这比只回答“它开源、Star 多、上手快”更有说服力。

### 13. 为什么不用 LangGraph 实现 Agent orchestration？

### 参考回答

> LangGraph 很适合把有状态、多步骤流程显式建模为 State、Node 和 Edge，也支持条件路由、检查点、中断恢复和子图。我们当时没有选择它，主要是因为场景仍处在快速验证阶段，流程较短，已有 OpenManus 原型和工具体系可以复用；如果同时迁移框架，会增加状态建模、框架学习和改造成本，而短期收益有限。因此这是基于项目阶段的取舍，并不代表 LangGraph 能力不足。

适合迁移到 LangGraph 的信号包括：

- 分支和回路变多，需要显式状态图。
- 长任务需要持久化、暂停、恢复和人工介入。
- 多个子 Agent 需要清晰的状态边界和 Handoff。
- 需要更强的执行回放、可视化和调试能力。

一句话总结：**OpenManus 更适合当时快速验证通用 Agent 循环；LangGraph 更适合把复杂、长期运行的状态流程显式工程化。最终仍要根据团队现有栈和业务约束选择。**

### 14. 多个 Agent 同时执行时会争抢哪些资源？

### 参考回答

资源争抢可以分为五类：

1. **模型资源**：API QPS/TPM、并发连接、Token 和费用预算，本地模型的 GPU 显存与推理槽位。
2. **计算资源**：CPU、内存、线程池、进程池和容器配额。
3. **存储资源**：数据库连接池、同一状态记录、向量库、缓存热点、文件和对象存储。
4. **工具资源**：浏览器会话、代码执行沙箱、第三方 API 配额、设备独占能力。
5. **逻辑资源**：同一任务状态、共享记忆、锁、消息队列分区以及用户级预算。

常见后果包括限流、延迟抖动、数据覆盖、重复副作用、死锁、成本失控和上下文串扰。

治理方法：全局及租户级配额、优先级队列、信号量、连接池、超时和背压；对共享状态使用乐观锁或版本号；副作用操作使用幂等键；为每个 Agent 分配 Token、时间和调用次数预算；独占工具通过租约管理，任务结束或超时后自动释放。

### 15. 多 Agent 如何做上下文和状态隔离？

### 参考回答

> 我会先把状态按租户、用户、会话、运行和 Agent 五级命名空间隔离。每个 Agent 只拿到完成当前子任务所需的最小上下文，而不是共享完整对话和全部记忆。父子 Agent 通过定义好的输入输出 Schema 传递任务和结果，公共黑板只保存允许共享的事实与产物。持久化层的每条记录都带 `tenant_id/session_id/run_id/agent_id`，读写同时进行服务端鉴权，不能只依赖 Prompt 要求 Agent 不越界。

还要处理：

- **并发一致性**：版本号、Compare-And-Swap、事务或针对热点资源的锁。
- **凭证隔离**：每个 Agent/任务使用短期、最小权限凭证。
- **执行隔离**：独立容器或沙箱，限制文件系统、网络和系统调用。
- **记忆隔离**：短期上下文默认随运行结束回收；长期记忆需明确写入策略、TTL 和删除机制。
- **数据流控制**：跨 Agent 消息进行 Schema、敏感信息和来源校验，防止恶意 Agent 或污染内容横向传播。

### 17. Workflow 和自治 Agent 有什么区别？

### 参考回答

| 维度 | Workflow | 自治 Agent |
| --- | --- | --- |
| 控制流 | 开发者预先定义节点与路径 | 模型根据目标和环境动态决定下一步 |
| 可预测性 | 高，易测试和审计 | 较低，可能产生未预期路径 |
| 灵活性 | 适合流程稳定、边界清晰的任务 | 适合开放式、步骤难预先穷举的任务 |
| 成本与延迟 | 通常更可控 | 通常调用次数更多，波动更大 |
| 故障定位 | 较容易 | 需要完整 Trace、状态快照和决策记录 |
| 风险 | 路径遗漏、规则僵化 | 幻觉、循环、越权和工具误用 |

> 二者不是非黑即白。生产系统通常采用混合模式：外围用确定性 Workflow 控制权限、预算、审批和关键路径；局部节点内允许 Agent 自主规划和选择工具。这样既保留灵活性，也能控制风险。

---

### 18. 如何防止 Prompt Injection 诱导 Agent 泄露 System Prompt 或绕过指令？

### 核心观点

Prompt Injection 很难仅靠更长的 System Prompt 根治。System Prompt 也不应包含真正的秘密。要假设模型可能被诱导，安全边界必须建立在模型之外。

### 参考回答

> 我会采用纵深防御。第一，区分系统指令、用户输入和外部内容，把网页、文档、邮件、RAG 片段和其他 Agent 消息都标记为不可信数据，不允许它们直接成为高权限指令。第二，System Prompt 不存 API Key、数据库密码等秘密；敏感数据按任务最小化注入，并做脱敏。第三，模型只负责提出工具调用意图，独立的 Tool Gateway 根据用户身份、资源范围和业务策略做确定性授权，拒绝越权调用。第四，对工具参数和模型输出做 Schema、注入、敏感信息及目标地址校验；高风险或不可逆操作要求人工确认。第五，代码执行和外部内容处理放入沙箱，限制网络出口、文件系统和运行时间。最后记录完整审计日志，通过红队用例持续测试直接注入、间接注入、编码混淆和多轮攻击。

如果面试官只问“如何防止 System Prompt 泄露”，可以补一句：

> 可以通过拒答策略和输出 DLP 降低泄露概率，但不应把 System Prompt 的保密性当作系统安全前提；真正的凭证和授权逻辑必须位于模型不可见、不可修改的服务端。

### 19. Agent 对工具调用不作限制会产生哪些风险？

### 参考回答

- **越权访问**：读取其他用户、租户或内部系统的数据。
- **数据泄露**：通过 HTTP 请求、邮件、日志或最终输出外传敏感信息。
- **破坏性副作用**：误删文件、修改数据库、发消息、下单或执行不可逆操作。
- **代码与基础设施风险**：命令注入、RCE、SSRF、访问云元数据或内网服务。
- **成本与可用性风险**：无限循环、递归调用、Token 消耗、API 配额耗尽和拒绝服务。
- **业务一致性风险**：重复调用产生重复扣款、重复发信或状态覆盖。
- **供应链风险**：调用被篡改的插件、MCP Server 或工具描述。
- **合规风险**：在未获得合法授权时处理个人信息或执行高影响决策。

可以总结为：工具把模型输出变成了现实世界的副作用，风险从“回答错误”升级为对机密性、完整性和可用性的直接影响。

### 20. 如何避免工具调用风险？

### 参考回答

1. **工具最小化**：只向当前 Agent 暴露完成任务必需的工具，读写工具分离。
2. **最小权限**：短期凭证、用户级身份、细粒度 Scope，禁止共享管理员凭证。
3. **独立授权**：每次调用在 Tool Gateway 重新验证用户、动作、资源和上下文；不信任模型给出的“我已获授权”。
4. **强参数校验**：JSON Schema、类型和范围检查；SQL 参数化；文件路径和 URL Allowlist；防 SSRF、命令注入和路径穿越。
5. **执行隔离**：代码放在容器/沙箱，限制 CPU、内存、时间、文件系统和网络出口。
6. **人机协同**：删除、转账、外发消息、权限变更等高风险动作必须二次确认；确认内容应绑定具体参数并设置有效期。
7. **预算和熔断**：限制最大步骤数、递归深度、Token、费用、并发、重试和调用频率。
8. **幂等和补偿**：副作用调用携带幂等键，必要时设计 Saga/补偿流程。
9. **监控审计**：记录调用者、工具、参数摘要、授权结果、返回状态和策略版本；异常行为告警。
10. **安全测试**：把 Prompt Injection、越权、恶意工具返回、循环调用和审批绕过加入 CI 回归集。

最重要的一句话：**模型负责建议动作，策略层决定能不能做，执行器负责安全地做。**

### 21. 为什么项目中不考虑多 Agent？

### 参考回答

> 我们评估后认为当前任务虽然有多个步骤，但角色边界不够独立，单 Agent 配合确定性工具和 Workflow 已经能满足正确率要求。如果强行拆成多 Agent，会增加模型调用、上下文传递、状态一致性和调试成本，端到端延迟也会上升。在没有证据表明多 Agent 能显著提升任务成功率之前，我们优先选择结构更简单、可观测性更好的方案。

可以说明未来的拆分条件：

- 子任务专业性强，需要不同模型、Prompt、工具或权限。
- 子任务能够并行，并行收益明显高于通信开销。
- 单 Agent 上下文过长，职责已经难以维护。
- 需要把高风险能力放在独立信任边界内。

“多 Agent 更高级”不是使用理由，必须有可测量的收益。

### 22. 如果进行多 Agent 拆分，会有哪些风险？

### 参考回答

- **协调复杂度**：任务分解错误、重复工作、遗漏、互相等待、死锁或活锁。
- **状态一致性**：多个 Agent 同时修改共享状态，产生覆盖、脏读和顺序问题。
- **上下文损失**：Handoff 时信息被压缩、误解或丢失，责任边界模糊。
- **错误级联**：上游幻觉成为下游“事实”，多个 Agent 相互强化错误。
- **安全边界扩大**：恶意或被注入的 Agent 通过消息影响其他 Agent，形成权限放大和横向移动。
- **资源开销**：更多 Token、工具调用、并发资源和更高尾延迟。
- **可观测性下降**：很难判断哪个 Agent、哪条消息导致最终错误。
- **版本兼容问题**：不同 Agent 的 Schema、Prompt 和能力版本不一致。

缓解方式包括：明确角色和 DAG、Schema 化通信、最小上下文传递、每个 Agent 独立权限、消息签名与来源标识、版本化协议、全链路 Trace、预算与终止条件、幂等机制，以及由确定性调度器而不是 Agent 自由广播消息。

### 23. 如何看待未来 AI 和编程的发展趋势？

### 参考回答

> 我认为 AI 会持续降低样板代码、信息检索和初稿实现的成本，开发者的重心会从“逐行写代码”向需求澄清、系统设计、任务拆解、约束表达、评测验证和生产治理迁移。但软件交付不只是生成代码，还包括理解模糊业务、处理复杂遗留系统、权衡性能与成本、保证安全合规以及对结果负责，所以短期内更像是工作方式重构，而不是简单替代开发者。
>
> 对个人而言，核心能力会变成两部分：一是扎实的计算机和工程基础，能判断 AI 输出是否正确；二是善用 AI，把需求写成可验证的规格，建立测试、评测和反馈闭环。Agent 还会让代码工具从“回答问题”走向“执行任务”，因此权限控制、可观测性和人机协作会越来越重要。

回答应避免两个极端：“AI 马上替代所有程序员”和“AI 只是自动补全、没有影响”。

### 25. Agent 扩展到大量设备，同时覆盖本地 Agent 和云端 Agent，如何设计？

### 总体思路

采用“云端控制面 + 分布式任务面 + 设备侧运行时”的分层架构。云端负责全局治理和重计算，设备侧负责低延迟、隐私敏感及必须访问本地资源的任务。

### 参考回答

> 首先把控制面和执行面分离。云端控制面维护设备注册、身份、能力目录、策略、模型/Agent 版本和任务调度；任务通过消息队列或设备网关下发。每台设备运行轻量 Agent Runtime，负责心跳、能力上报、本地工具调用、资源限制、离线队列和结果回传。调度器根据数据位置、隐私等级、延迟、设备在线状态、算力和成本决定任务在本地执行、云端执行，还是拆分执行。

关键设计点：

1. **设备身份与安全通信**：每台设备有独立身份和可轮换证书，使用 mTLS；任务携带租户、用户、能力 Scope、有效期和签名。
2. **能力注册与路由**：设备上报 OS、模型、工具、算力和当前负载；调度器只把任务发给满足能力与权限要求的节点。
3. **状态模型**：任务使用全局唯一 `task_id` 和版本号；云端保存权威任务状态，设备保存必要快照。采用事件日志、幂等消费和至少一次投递，避免断网重连后重复执行副作用。
4. **云边协同**：隐私数据尽量留在本地，只上传脱敏摘要；大模型推理、跨设备聚合放在云端；实时控制或本地文件访问放在设备端。
5. **离线与故障恢复**：设备断网时可执行被允许的本地任务并缓存事件；恢复连接后增量同步。任务有租约、超时和取消机制，设备失联后可重新调度安全任务。
6. **版本治理**：Agent、Prompt、工具协议和策略均版本化，支持灰度、兼容性检查、回滚和远程吊销。
7. **资源治理**：按租户和设备设置并发、Token、CPU、内存、电量和网络预算；通过背压、优先级和熔断保护设备与云服务。
8. **可观测性**：用 `trace_id → task_id → device_id → run_id → step_id` 串联全链路，同时对本地日志做脱敏和采样。
9. **高风险操作**：权限判断在云端策略服务和设备本地执行器双重校验；高风险动作需要参数绑定的用户确认，不能只信任云端 Agent 发来的自然语言指令。

可以用一句话收尾：

> 这个设计的核心不是简单把同一个 Agent 复制到很多设备，而是统一身份、能力、任务协议和策略，同时允许本地与云端根据隐私、延迟和算力进行动态分工。

## 面试前速记

1. Agent 结果不能承诺绝对正确，要有证据、规则校验、评测和人工兜底。
2. JSON 只是格式，必须配合 Schema 校验和失败处理。
3. OpenManus 与 LangGraph 的选择是项目阶段和工程约束的取舍。
4. 多 Agent 的价值必须大于通信、一致性、成本和安全开销。
5. Prompt 不是安全边界；模型外的权限、沙箱、审批和审计才是。
6. 工具调用遵循最小功能、最小权限、最小自主性。
7. 大规模云边 Agent 的关键词：控制面/执行面分离、设备身份、能力注册、幂等任务、离线恢复、灰度版本和全链路追踪。
