### 1. 深拷贝和浅拷贝。

浅拷贝只复制对象本身：基本类型字段复制值，引用类型字段只复制地址，两个对象共享同一份底层数据。深拷贝则递归复制引用类型字段，副本之间完全独立。

Java 实现深拷贝的几种方式：

1. 手动重写 `clone()`：`Object.clone()` 默认是浅拷贝，需要逐字段递归 `clone`。
2. 序列化 / 反序列化：原生序列化或 Jackson、Gson 转 JSON 再转回，最省事但性能差。
3. 拷贝构造器 / 静态工厂：`new Foo(other)` 逐字段深复制，最可控，生产中主流。
4. 工具类：`commons-lang` 的 `SerializationUtils.clone()`。

三个边界：

- `Arrays.copyOf` 是浅拷贝，元素为对象时照样共享。
- 不可变对象（`String`、包装类）不需要深拷贝，复制引用即可。
- 深拷贝要处理循环引用，否则无限递归；手写实现时用 identity map 记录已拷贝对象。

### 2. `finally` 一定会执行吗？系统发生错误的时候呢？

结论：不一定。前提是 JVM 仍然存活且控制流能走到 finally 语句块。

会执行：`try` 中的 `return`、`break`、`continue`，finally 在返回值求值完成后、真正返回前执行；`try` 中抛异常，无论是否被 catch，finally 都会执行。

不会执行：`System.exit()` 或 `Runtime.halt()` 终止 JVM；进程被强杀（`kill -9`）、断电、JVM 崩溃；守护线程随主线程结束而终止时；`try` 中死循环或死锁，控制流走不到 finally。

关于“系统发生错误”：`OutOfMemoryError`、`StackOverflowError` 虽然是 `Error`，但同属 `Throwable`，**只要 JVM 还活着，finally 照样会执行**。风险在于堆已耗尽时 finally 内再分配对象可能二次 OOM，栈已溢出时 finally 也可能因空间不足而执行失败。真正让 finally 失效的是进程或虚拟机层面的终结，而非异常本身。

必接的经典坑：

- finally 中 `return` 会吞掉 try 的返回值和异常。
- finally 中修改基本类型变量不影响 try 已算好的返回值（`return x` 的值早已入栈），但修改引用对象的内容会生效。
- finally 中抛异常会覆盖原始异常，排障时最坑。

### 3. AOP 失效的场景。

根因：Spring AOP 基于代理（JDK 动态代理 / CGLIB）。失效只有两类原因——调用没经过代理，或代理拦不住这个方法。

| 场景 | 原因 |
| --- | --- |
| 同类内部自调用 `this.foo()` | 不走代理，直接调用原对象；`@Transactional`、`@Async` 失效最常见的原因 |
| 方法非 public | Spring AOP 默认只拦截 public；JDK 代理只能代理接口方法 |
| 方法或类为 `final`、`static` | CGLIB 靠继承生成子类，无法覆盖 |
| 对象不是 Spring Bean | `new` 出来的、没有对应注解、未被扫描到 |
| `@Aspect` 类未被 Spring 管理、切点表达式写错 | 根本没有生成通知 |
| 循环依赖拿到早期引用 | 拿到的是原始对象而非代理（少见） |

自调用的标准解法：拆到另一个 Bean 中注入调用（最推荐）；`AopContext.currentProxy()`，需开启 `exposeProxy = true`；注入自身并用 `@Lazy` 打破循环依赖。

### 4. 调用者拒绝策略会出现什么问题？

先澄清：`AbortPolicy` 是抛 `RejectedExecutionException`，不是“抛弃”；静默丢弃的是 `DiscardPolicy`。另外“队列满且线程数未达 max 时新建线程”属于线程池扩容流程，不是拒绝策略。

四种标准策略：

| 策略 | 行为 | 是否丢任务 |
| --- | --- | --- |
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 不丢，但提交方需处理异常 |
| `CallerRunsPolicy` | 由提交任务的线程自己执行 | 不丢 |
| `DiscardPolicy` | 静默丢弃 | 丢，且无感知 |
| `DiscardOldestPolicy` | 丢弃队首最老任务后重新提交 | 丢最老的 |

`CallerRunsPolicy` 的问题（本题核心）：

1. 阻塞调用者线程，这是最严重的。若提交方是 Tomcat 工作线程，它被拉去执行业务任务，Tomcat 线程池被占满会导致整个服务不可用，故障从线程池扩散到 Web 容器。
2. 可能死锁：调用者持有锁而任务需要同一把锁；或调用者 `future.get()` 等待结果，而任务正由自己执行。
3. 超时与响应时间失控：任务耗时计入调用方，调用链超时设置失真。
4. 边界：线程池已 shutdown 时不执行（源码为 `if (!e.isShutdown()) r.run();`），会静默丢弃。

它也是四个策略里唯一既不丢任务、又能形成反压的策略，适合对丢失零容忍且可接受反压的场景（离线批处理、消息消费）。线上交易链路一般不用，更常见的是自定义 `RejectedExecutionHandler`：落库或投 MQ 后补偿、降级告警。

### 5. 阻塞队列是如何管理线程的？

机制不是 `wait` / `notify`，而是 `ReentrantLock` + `Condition`。

- 队列空时，消费者 `take()` 进入 `notEmpty` 条件队列 `await()`，并释放锁挂起。
- 队列满时，生产者 `put()` 进入 `notFull` 条件队列 `await()`。
- 入队成功调用 `notEmpty.signal()` 唤醒一个消费者；出队成功调用 `notFull.signal()` 唤醒一个生产者。

优于 `synchronized` + `wait` / `notify` 之处：一把锁配两个 Condition，生产者只唤醒消费者、消费者只唤醒生产者，不会唤醒错对象；`synchronized` 只有一个等待集，只能 `notifyAll` 全唤醒后靠 while 循环重新判断，无效竞争多。此外支持公平锁（`new ReentrantLock(true)`，FIFO 防饥饿），默认非公平换吞吐。

实现差异：`ArrayBlockingQueue` 一把锁 + 两个 Condition，读写在同一条临界区；`LinkedBlockingQueue` 用 `putLock` / `takeLock` 两把锁实现读写分离，吞吐更高，这也是它默认容量接近 `Integer.MAX_VALUE`（即“无界”）的原因。

与线程池的衔接：阻塞队列本身不管理线程，只提供阻塞点。真正决定线程生灭的是线程池 Worker 的 `getTask()`——核心线程调 `workQueue.take()` 无限阻塞，非核心线程调 `workQueue.poll(keepAliveTime, NANOSECONDS)`，超时返回 null 则线程退出。

### 6. 线程池的工作原理。

`execute()` 的提交流程：

1. 线程数 < `corePoolSize`，直接新建核心线程执行任务。这一步不排队，即使有空闲线程也先开新的，直到核心数满。
2. 否则尝试入队 `workQueue.offer(task)`。入队成功则等空闲线程来取；入队后要再检查线程池状态，若已 shutdown 则回滚出队并拒绝。
3. 入队失败（队列满）且线程数 < `maxPoolSize`，新建非核心线程执行任务。
4. 仍失败，执行拒绝策略。

顺序是 core → queue → max → reject，**先排队再加线程**，与直觉相反，是必考点。

线程复用：`Worker` 内部循环调用 `getTask()` 从队列取任务，取到就 `run()`，取不到按第 5 题的逻辑处理。`allowCoreThreadTimeOut(true)` 可让核心线程也超时回收。

参数补全：除核心线程数、最大线程数、阻塞队列、拒绝策略外，还有 `keepAliveTime`、时间单位、线程工厂（必须自定义命名，线上 dump 排查依赖它）。

两个必说的坑：

- 无界队列会让 `maxPoolSize` 形同虚设。`LinkedBlockingQueue` 默认容量接近无限，任务永远能入队，第 3、4 步走不到，拒绝策略永不触发，风险是任务堆积到 OOM。
- 因此阿里规约禁止使用 `Executors`：`newFixedThreadPool` / `newSingleThreadExecutor` 用无界队列导致 OOM；`newCachedThreadPool` 队列为 `SynchronousQueue` 且 `maxPoolSize` 为 `Integer.MAX_VALUE`，会无限创建线程。应手动 `new ThreadPoolExecutor` 显式传参。

线程数估算：CPU 密集取 `N + 1`；IO 密集取 `2N` 或按阻塞系数 `N × (1 + W / C)`。

### 7. `HashMap` 多线程并发会出现什么问题？

JDK 7：头插法配合并发扩容会反转链表顺序并形成环形链表，之后 `get` 遍历到该桶会死循环、CPU 占满；同时存在并发 put 互相覆盖导致的数据丢失。

JDK 8：扩容时用 `loHead` / `loTail` 与 `hiHead` / `hiTail` 拆成两条链并保持相对顺序，环形链表问题消失。但依然不安全，只是换了表现形式：`tab[i] = newNode()` 是竞态写，并发 put 会覆盖丢数据；`size` 计数不准；无可见性保证，`get` 可能读到旧值或 null；并发 treeify 也能破坏红黑树结构。

需澄清：`HashMap` 本身没有任何锁，正因为完全未同步才不安全。做同步的是 `Hashtable`（方法级 `synchronized`，锁整个对象，性能差）和 `Collections.synchronizedMap`。

`ConcurrentHashMap`：JDK 7 为分段锁 `Segment`（默认 16 段）；JDK 8 改为 CAS 插入 + `synchronized` 只锁单个桶的头节点，锁粒度细到桶级，并支持多线程协助扩容（`helpTransfer`），用 `baseCount` + `CounterCell` 分散统计 size。

### 8. 哈希冲突的解决方法。

| 方法 | 做法 | 典型使用者 |
| --- | --- | --- |
| 链地址法（拉链法） | 同一下标挂成链表 | `HashMap`、`ConcurrentHashMap` |
| 开放定址法 | 数组内往后找空位（线性 / 二次 / 伪随机探测） | `ThreadLocalMap`、Python dict |
| 再哈希法 | 冲突时用第二个哈希函数重算 | 布隆过滤器、Cuckoo Hashing |
| 公共溢出区 | 冲突元素统一放入另一个溢出表 | 实际少用 |

开放定址法的坑：删除要打墓碑标记，直接置空会切断探测链；容易产生堆积（clustering）。

`HashMap` 的做法是拉链法 + 扰动函数 + 树化：`h = key.hashCode() ^ (h >>> 16)` 让高 16 位参与运算以减少冲突；链表长度 ≥ 8 且数组容量 ≥ 64 时转红黑树，最坏查询由 O(n) 降到 O(log n)。

易混点：`HashMap` 语境下的“再 hash”指扩容 rehash。因为容量是 2 的幂，用 `hash & (n - 1)` 定位，扩容后只需看多出的那一位是 0 还是 1，元素要么留在原下标，要么移到“原下标 + 旧容量”，无需重算 hash；这与冲突解决中的“再哈希法”是两回事。

### 9. 场景题：实现分号器（原帖用字，疑为“发号器”笔误，待确认）。

按“发号器”理解，先给方案选型：UUID 本地生成无网络开销，但无序、占空间，作 MySQL 主键会引起页分裂；数据库自增 / 号段模式有序、简单，但依赖 DB 且需处理单点与性能（双 buffer 预取）；Redis INCR 有序、性能好，但依赖 Redis 可用性并需持久化防丢；雪花算法本地生成、趋势递增、无网络依赖、性能高，是主流选择。生产上常见方案是美团 Leaf（号段 + 雪花双模式）、百度 UidGenerator。

雪花算法 64 位结构：

```
 1 位  符号位      固定 0，保证 ID 为正
41 位  时间戳      毫秒级，从自定义 epoch 起算，可用约 69 年
10 位  机器 ID     可拆 5 位 datacenterId + 5 位 workerId，支持 1024 个节点
12 位  序列号      同一毫秒内自增，单毫秒 4096 个 ID
```

单机 QPS ≈ 4096 × 1000 ≈ 409.6 万 / 秒。唯一性由时间戳、机器 ID、序列号三者组合保证，只要三者不同时重复，ID 就唯一。

机器 ID 的分配不是靠 IP。正确做法是由统一的位置分配（配置中心 / Zookeeper / Redis 注册），保证每台机器拿到不同的 10 位。用 IP 派生 workerId 是常见简化做法，但容器化环境下 Pod 重建后 IP 变化，不可靠。

时钟回拨（Clock Backwards）必须给出解法，只提风险等于没答：

1. 回拨幅度小（如 < 5ms）时自旋等待，追平上次时间戳。
2. 幅度大时直接抛异常并告警，宁可拒绝服务也不生成重复 ID。
3. 启动时用上次记录的最大时间戳兜底，不倒退。
4. 换思路：用号段模式（美团 Leaf-segment）、百度 UidGenerator，从根上绕开系统时钟依赖。
