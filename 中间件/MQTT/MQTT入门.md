
### MQTT报文

#### 15种控制报文类型

| 报文类别 | 报文名称        | 报文说明                                                                       |
| ---- | ----------- | -------------------------------------------------------------------------- |
| 连接   | CONNECT     | 用于客户端向服务端发起连接                                                              |
| 连接   | CONNACK     | 作为响应返回连接的结果                                                                |
| 连接   | DISCONNECT  | 想要结束通信，或者遇到了一个必须终止连接的错误，发送该报文关闭网络连接                                        |
| 连接   | AUTH        | 是 MQTT 5.0 引入的全新的报文类型，它仅用于增强认证，为客户端和服务端提供更安全的身份验证                          |
| 连接   | PINGREQ     | 报文用于连接保活和探活，客户端定期发出 PINGREQ 报文向服务端表示自己仍然活跃，然后根据 PINGRESP 报文是否及时返回判断服务端是否活跃 |
| 连接   | PINGRESP    | 同上                                                                         |
| 发布   | PUBLISH     | 用于发布消息                                                                     |
| 发布   | PUBACK      | 分别用于 QoS 1 和 QoS 2 消息的确认流程                                                 |
| 发布   | PUBREC      | 同上                                                                         |
| 发布   | PUBREL      | 同上                                                                         |
| 发布   | PUBCOMP     | 同上                                                                         |
| 订阅   | SUBSCRIBE   | 用于客户端向服务端发起订阅                                                              |
| 订阅   | UNSUBSCRIBE | 用于客户端向服务端发起取消订阅                                                            |

| 订阅   | UNSUBACK    | 返回取消订阅结果                                                                   |

### Qos 消息服务质量等级

底层使用TCP, 但是需要引入Qos机制保证消息不丢失


| QoS 等级 | 含义         | 传输保证            | 丢失/重复           | 应用场景                  |
| ------ | ---------- | --------------- | --------------- | --------------------- |
| 0      | **最多发送一次** | 即发即弃，不需要应答。     | 可能会**丢失**，不会重复。 | 传感器数据、高频、可容忍丢失。       |
| 1      | **至少发送一次** | 引入应答和重传机制。      | 不会丢失，但可能**重复**。 | 传输重要数据，需在应用层实现幂等性。    |
| 2      | **仅有一次发送** | 复杂的两次请求/响应四步握手。 | 不丢失，不重复。        | 金融交易、航空控制等对可靠性要求极高领域。 |



Qos2底层使用的是双确认机制, 参考TCP握手差不多



### 主题

主题是 MQTT 中用于消息分类和路由的字符串标识符。

- **本质是字符串。**
- **分层：** 使用 `/` 进行层级划分，例如 `home/sensor/temp`。
- **规范：** 不建议以 `/` 开头或结尾（如 `chat/`、`/chat`），以避免歧义。

#### 主题通配符

通配符只用于 **订阅主题过滤器**，不能用于发布的主题名称。

| 通配符 | 名称 | 含义 | 示例 | 匹配 |
| --- | --- | --- | --- | --- |
| `+` | **加号通配符** | 匹配**一个**层级。 | `a/+/c` | 匹配 `a/b/c`，不匹配 `a/b/d/c` 或 `a//c`。 |
| `#` | **井号通配符** | 匹配**零个或多个**层级，必须放在主题过滤器的**最后**。 | `a/b/#` | 匹配 `a/b/c`、`a/b/d/e`、`a/b`。 |

#### 系统主题

系统主题以 `$SYS/` 开头，用于获取 Broker 自身的运行时状态和统计信息。

- **特点：** 默认不允许远程客户端订阅（取决于 Broker 配置），通常用于监控 Broker 性能。
- **用途：** 获取集群状态、客户端连接/离线事件（如 `$SYS/brokers/+/clients/+/connected`）等。




### 消息详解

#### 保留消息

- **普通消息：** 消息发布后，Broker 立即将消息分发给所有当前订阅者，然后删除消息。
- **保留消息：** 消息发布时设置 **Retain 标志为 True**。Broker 会将该消息存储起来，作为该主题的**最新状态**。

**特点：**
1. **每一个主题最多只有一条保留消息**（即最后一条带有 Retain 标志的消息）。
2. 客户端在**建立新的订阅**时，Broker 会检查该主题是否有保留消息，并立即发送给客户端。
3. 必须在**保留消息发布之后**，客户端再订阅该主题才能收到。如果在保留消息发布前就已订阅，收到的只是后续的普通消息。

删除保留消息的方法：
- 发送空内容的保留消息： 发布一个 空载荷 且 Retain 标志为 True 的消息到该主题。
- 设置过期时间： 在发布保留消息时设置 Message Expiry Interval，使其在达到时间后自动失效。

保留消息独立于会话。 即使使用 Clean Start = 1 创建新会话，只要你重新订阅了该主题，Broker 依然会发送保留消息。

#### 消息过期间隔

这是 MQTT 5.0 引入的属性。
- **设置：** 在 `PUBLISH` 报文中设置该属性（单位为秒）。
- **作用：** Broker 存储的消息（包括 QoS 1/2 的离线消息和保留消息）会在超过此时间后自动删除。这可以避免 Broker 被长时间未上线的客户端的离线消息占满。


#### 遗嘱消息

遗嘱消息用于处理客户端**非正常断开连接**（如网络中断、断电等）的情况。

**注册流程：** 升级网络设备

遗嘱消息的设置发生在客户端发送 **`CONNECT` 报文** 时。

| 字段名称 | 作用说明 | 是否必需 |
| --- | --- | --- |
| **Will Flag（遗嘱标志）** | 设置为 `1`，表示客户端想要设置一个遗嘱消息。 | 是（开启功能） |
| **Will Topic（遗嘱主题）** | **必需。** 指定当客户端非正常断开连接时，Broker 应该将遗嘱消息发布到哪个主题上。 | 是 |
| **Will Payload（遗嘱载荷）** | **必需。** 指定遗嘱消息的具体内容（数据）。 | 是 |
| **Will QoS（遗嘱 QoS 等级）** | 指定 Broker 发布遗嘱消息时应使用的 QoS 等级。 | 是 |
| **Will Retain（遗嘱保留标志）** | 设置为 `1`，表示 Broker 发布遗嘱消息后，应将其作为**保留消息**存储。 | 可选 |
| **Will Delay Interval（遗嘱延迟发送）** | 客户端断开连接后，延迟多久发布遗嘱消息（秒）。 | 可选 |

**发布条件：**

- **触发：** 客户端**意外断开**连接（如 Keep Alive 超时、网络错误）。Broker 会发布遗嘱消息。
- **不触发：** 客户端**正常关闭**（发送 `DISCONNECT` 报文），或 Broker 正常关闭且客户端没有持久会话需要保留。

**应用场景：** 实现设备“心跳”或在线状态监控。设备上线时，客户端可以订阅遗嘱主题，并在收到遗嘱消息时判断该设备已失联。
