### 简介
* Kafka作用
	* 缓存/削峰
	* 解耦
	* 异步通信
* 模式:
	* 点对点式消费: 同一个消费者组内分工消费，消费后不自动删除消息
	* 发布/订阅: 不同消费者组独立消费同一个topic，消息按Kafka的保留策略清理
* 架构
	* Producer
	* Broker
		* Topic: 可以跨多个Broker分布
			* Partition: 每个分区有自己的副本
				* Leader
				* Follower副本
	* Consumer:
		* Consumer Group: 对于普通消费者组，**一个分区同一时刻只分配给组内一个消费者，但一个消费者可以负责多个分区**；不同组独立消费，互不分摊消息
	* KRaft Controller集群

### Producer

#### 数据发送原理
* 业务线程调用send（不一定是main线程，通常加入缓冲区后返回）
* Interceptors 拦截器（可选）
* Serializer 序列化器
* Partitioner 分区器: 决定消息进入哪个分区
* RecordAccumulator: 缓存消息批次，buffer.memory默认32MiB，各分区共享
	* Deque: 一个队列对应一个Topic的一个Partition，队列中存放ProducerBatch，每个批次包含多条消息
	* batch.size默认16KiB，按分区分别攒批
* Sender线程:
	* 批次满了，或等待达到linger.ms，就可以发送，不必同时满足
	* linger.ms: 批次没满也会在达到等待时间后准备发送（4.0起Java客户端默认5ms，旧版默认0）
* Selector: 通过NetworkClient参与网络I/O，将请求发送到目标分区的Leader

ACK 应答级别
- 0: Producer不等待Broker的ack
- 1: Leader写入本地日志后返回ack，不等待Follower全部复制
- -1(all): 当前ISR中的副本完成复制后，由Leader向Producer返回ack；ISR本身包含Leader，不是所有副本都直接向Producer应答

#### 异步发送

```java
public static void main(String[] args) throws InterruptedException {  
    Properties props = new Properties();  
    props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:29092,localhost:39092,localhost:49092");  
    props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");  
    props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");  
  
    try (Producer<String, String> producer = new KafkaProducer<>(props)) {  
        for (int i = 0; i < 10; i++) {  
            producer.send(new ProducerRecord<>("orders", "event-" + i));  
            Thread.sleep(100); // 每次发送间隔约 100ms
        }
    }  
  
}
```

#### 数据分区
* 采用分区,可以合理使用存储资源
* 提高并行度


> 默认分区策略: 
> 1. 指定了partition：直接使用指定分区。
> 2. 没指定partition，但有key：对序列化后的key计算hash，取非负值后对分区数取模；分区数不变时，相同key进入同一分区。
> 3. partition和key都没指定：使用粘性分区，连续向同一分区发送；累计数据达到batch.size后再选择分区，不是每条消息轮询分区。


> 例子: 同一张MySQL表的消息进入同一分区，可以把表名当key（同一Topic、分区数不变且使用默认key分区策略）。

#### 如何提高吞吐量
> Java Kafka 4.2客户端默认linger.ms为5ms，batch.size默认16KiB；旧版客户端linger.ms默认为0。

- batch.size: 批次大小,默认16k, 可以改为32k等
* linger.ms: 可适当增大攒批时间，但会增加低流量时的等待，需要结合延迟要求调整
* compression.type: 压缩数据提高吞吐量
* buffer.memory: 待发送消息的缓冲内存预算，默认32MiB，可以按需调整为64MiB



#### 如何保证数据可靠性? 

> 数据可靠性需要结合ACK、分区副本数、min.insync.replicas、重试和失败处理判断；ACK不代表Consumer处理成功。

ACK 应答级别
- 0: Producer不等待Broker的ack
- 1: Leader写入本地日志后返回ack，不等待Follower全部复制
- -1(all): 当前ISR中的副本完成复制后，由Leader向Producer返回ack；ISR本身包含Leader，不是所有副本都直接向Producer应答

- 0的问题:
	- Producer不等待写入确认，消息可能根本没到Broker，也可能在副本复制前因Leader故障丢失
- 1的问题:
	- Producer已经收到Leader的ack，但Follower还没复制时Leader故障，消息可能丢失
- -1的问题:
	- 等待当前ISR中的副本完成复制，可靠性还取决于min.insync.replicas
	- Follower故障或落后可能导致等待；退出ISR后不再等待它，不是固定卡30s
	- replica.lag.time.max.ms默认30s，长期不拉取或未追上Leader的Follower会被移出ISR
	- 如果所有Follower退出ISR而Leader还活着，ISR只剩Leader，不是空集合；min.insync.replicas=1时仍可能写入成功，=2时不能成功


> 常见可靠性配置：acks=all、分区副本数=3、min.insync.replicas=2；ISR不足2时写入失败，需要处理最终发送失败。

```java
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
// min.insync.replicas=2是Topic/Broker配置，不是Producer配置。
```

#### 数据重复性问题?

> 未启用幂等性时：消息已写入并复制，但ACK丢失或Leader在返回ACK前故障，Producer重试可能再次写入同一条消息。
> 当前4.2客户端默认开启幂等性，可以消除客户端自动重试造成的重复；业务代码再次调用send发送同一内容，仍算新消息。


- ***At Least Once(至少一次)***: 允许重试以避免漏交付，但可能重复；生产侧可靠性配置与消费侧Offset提交都需要配合，不能只由ACK级别定义
- ***At Most Once(最多一次)***: 允许丢失，但不重复交付；acks=0不等待确认、无法根据Broker应答重试，但不能防止业务主动重复发送
- ***Exactly Once(精确一次)***: 要明确保证范围；Kafka消费→处理→再写Kafka时，需要将输出消息和消费Offset放入同一事务，下游按read_committed读取

#### 幂等性

* Broker基于PID、Epoch及每分区的SeqNumber识别重复批次，避免客户端自动重试重复写入。
* 同一Producer会话内，分别保证各分区的重试不重复；不保证跨分区的原子提交，也不按消息内容去重。
* 非事务Producer重建后通常获得新PID；不能靠普通幂等性识别重启后业务重新发送的相同消息。
* Kafka 3.0起默认开启幂等性，但与acks等配置冲突时可能被关闭；显式开启却存在冲突会报错。
* 幂等性要求acks=all、retries>0、max.in.flight.requests.per.connection<=5。

#### Kafka事务

* 把多条消息（可以跨分区、跨Topic）作为一个整体提交或中止。
* 配置transactional.id会启用事务能力并隐含开启幂等性，还需要显式调用事务API。
* transactional.id标识逻辑生产者，应在重启后保持稳定；不同并发实例不能共用，否则旧实例会被隔离。
* 流程：initTransactions()初始化一次 → beginTransaction() → send()多条消息 → commitTransaction()；中止时调用abortTransaction()。
* 消息在提交前就可能已写入Broker；中止是标记事务失败，不是立即物理删除消息。
* Consumer配置isolation.level=read_committed，才会过滤未提交和已中止事务的消息；默认read_uncommitted仍可能读到它们。
* Kafka消费→处理→再写Kafka：关闭自动提交，用sendOffsetsToTransaction()把下一条待消费的Offset和输出消息一起提交；中止后还需要恢复消费位置再处理。
* 事务不自动覆盖MySQL更新，也不能按订单号消除业务重复发送；这些仍需业务幂等或跨系统一致性方案。
