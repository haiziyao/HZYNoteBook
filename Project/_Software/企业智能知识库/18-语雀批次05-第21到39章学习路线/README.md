# 语雀第 21～39 章学习路线

## 1. 筛选结论

第 21～39 章共 19 章。按照项目的核心价值筛选，后续真正值得深入学习的是六个板块：

1. 第 21～22 章：Neo4j 与 KAG。
2. 第 23 章：智能搜索与双 Elasticsearch 索引。
3. 第 24 章：RabbitMQ 异步音视频转码。
4. 第 29 章：事件驱动统计系统。
5. 第 37 章：多格式文件解析进入 RAG/KAG/全文搜索。
6. 第 25、35 章中与团队和检索权限隔离有关的部分。

第 39 章的 MongoDB 自动保存快照具有一定学习价值，但不是知识库智能检索主线。其余章节以普通 CRUD、前端功能、通用安全机制或已学内容的完善为主，可以快速浏览。

## 2. 第一梯队：必须深入

### 2.1 第 21～22 章：Neo4j 与 KAG

第 21 章需要掌握：

- Node、Label、Property。
- Relationship 的类型、方向和属性。
- Path、多跳查询和最短路径。
- Cypher 的 `MATCH`、`CREATE`、`MERGE`、`DETACH DELETE`。
- Spring Data Neo4j 的 `@Node`、`@Relationship` 和 Repository。
- 复杂查询为什么要使用 `Neo4jClient` 执行自定义 Cypher。

第 22 章核心链路：

```text
文档发布
→ RabbitMQ异步触发知识图谱构建
→ 文档分块
→ LLM提取实体和实体关系
→ 写入Neo4j
→ Document -[:HAS_CHUNK]-> Chunk
→ Chunk -[:MENTIONS]-> Entity
→ Entity -[业务关系]-> Entity
→ 用户提问时查询相关节点和路径
→ 将图上下文加入Prompt
```

必须回答的问题：

- 为什么 MySQL、Elasticsearch、Neo4j 要保存同一文档的不同数据形态？
- LLM 如何从非结构化文档中提取实体和关系？
- 重复构图如何保证幂等？
- 文档更新、删除以后如何重建或删除图数据？
- Neo4j 与文档服务之间如何实现最终一致性？
- KAG 相比普通 RAG 多提供了什么信息？

### 2.2 第 23 章：智能搜索

第 23 章的一部分内容和第 20 章重复，不需要重新学习 Embedding、RRF 和 Rerank。重点是两个检索入口的职责划分：

```text
kb-search
→ kb_document索引
→ 文档级BM25搜索
→ 搜索建议、搜索历史、热门搜索、高亮和分页

kb-ai
→ kb_chunk索引
→ Chunk级BM25 + 向量检索
→ RRF + Rerank
→ RAG问答
```

必须理解：

- 为什么需要 `kb_document` 和 `kb_chunk` 两个索引？
- 普通搜索返回文档，RAG 检索返回 Chunk，二者为什么不能完全共用一个接口？
- 文档发布、更新和删除以后，两个索引如何同步？
- `kb-search`、`kb-ai`、`kb-document` 如何跨服务协作？
- Elasticsearch 写入失败时如何重试和重建？
- 团队、作者和文档状态等权限条件如何真正进入检索查询？

### 2.3 第 24 章：异步音视频转码

该功能不是知识库智能检索主线，但它是项目中非常典型的 RabbitMQ 耗时任务案例。

```text
上传原始音视频到RustFS
→ MySQL记录文件元数据
→ 发送RabbitMQ转码消息
→ TranscodeConsumer消费消息
→ FFprobe提取时长、分辨率、码率
→ FFmpeg生成360p/720p HLS
→ 生成缩略图
→ 上传转码结果到RustFS
→ 更新MySQL转码状态
```

转码状态机：

```text
PENDING → PROCESSING → DONE
                     → FAILED
```

重点不是记 FFmpeg 命令，而是理解：

- 为什么转码必须异步？
- RabbitMQ 消息应携带哪些任务信息？
- 重复消费时如何避免重复转码和重复上传？
- 消费者应该在什么时候手动 ACK？
- 服务在下载、转码、上传或更新数据库阶段崩溃分别会留下什么垃圾数据？
- MySQL 状态与 RustFS 对象不一致时如何补偿？
- HLS 为什么适合在线播放？

### 2.4 第 29 章：事件驱动统计系统

这是后续章节中最有分布式系统价值的案例之一。

```text
文档浏览/点赞/评论
→ kb-document发布统计事件
→ RabbitMQ
→ kb-statistics消费
→ 写入原始行为记录
→ Redis更新实时计数
→ 定时任务聚合
→ 写入文档/用户预聚合表
→ 查询结果进入Redis缓存
```

三类数据的职责：

- MySQL 原始行为数据：负责追溯和重新计算。
- Redis 实时计数：快速展示近期数据。
- MySQL 预聚合数据：用于趋势、排行榜和报表查询。

必须回答的问题：

- 为什么不能在每次统计查询时扫描所有行为明细？
- MQ 重复消费是否会让浏览量重复增加？
- 如何通过事件 ID 或业务唯一键保证消费幂等？
- Redis 与 MySQL 统计不一致时以谁为准？
- 定时聚合任务重复执行时如何避免重复统计？
- 实时统计和离线统计分别解决什么问题？
- 缓存失效以后如何回源？

### 2.5 第 37 章：多格式文件解析

这一章把文件上传和 RAG/KAG 构建真正连接起来：

```text
Word/PDF/Excel/PPT上传
→ kb-document通过Feign调用kb-file保存文件
→ 根据文件类型选择解析器
→ POI/PDFBox提取内容
→ 转换成统一Markdown
→ 创建文档
→ 审核/发布
→ 异步构建RAG、KAG和全文搜索索引
```

必须理解：

- 为什么不同格式最终统一转换成 Markdown？
- 标题、段落和表格结构为什么会影响 RAG 分块质量？
- `multipart/form-data` 如何通过 OpenFeign 跨服务传递？
- 上传成功但解析失败时如何处理 RustFS 文件？
- 解析成功但创建文档失败时是否会产生孤儿对象？
- 大文件解析为什么不适合长期占用 HTTP 请求线程？
- 扫描版 PDF 为什么无法直接提取文字，什么时候需要 OCR？

解析库的具体 API 可以选择性阅读，不需要逐行研究 PDFBox 和 POI 的底层代码。

### 第 39 章值得记住的链路

```text
编辑器每30秒检测内容变化
→ 更新当前草稿
→ CompletableFuture异步写MongoDB历史快照
→ 浏览器localStorage作为最后兜底
```

它体现了 MySQL 当前状态、MongoDB 历史快照和浏览器本地兜底的分层设计，但属于编辑体验而非智能知识库主线。

## 5. 不能照单全收的架构设计

### 5.1 第 28 章的跨库视图

文章让 `kb-user-auth` 通过 MySQL 跨库视图查询 `kb_document`。这样可以减少一次 HTTP 调用，但会带来：

- 用户服务依赖文档库的表结构。
- 两个数据库难以独立部署和迁移。
- 文档表结构变化可能直接影响用户服务。
- 微服务的数据所有权被破坏。

这种方案更接近共享数据库架构，适合规模较小或部署环境固定的系统，不应直接当作标准微服务最佳实践。

### 5.2 第 36 章直接查询配置表

文章将“其他微服务通过 `JdbcTemplate` 直接查询 `kb_system_config`”称为消费者解耦。实际上，它只是取消了 HTTP 依赖，同时增加了数据库结构和连接层面的耦合。

更合理的思路通常是：

```text
配置服务或Nacos发布配置
→ Redis或本地缓存保存可用副本
→ MQ/Nacos监听配置变化
→ 各微服务刷新本地配置
```

## 6. 企业知识库不能忽略的权限问题

团队管理和 RBAC 本身可以少看，但权限在检索链路中的落地不能跳过。

```text
用户身份与角色
→ 可访问团队/文档范围
→ MySQL文档查询条件
→ Elasticsearch文档和Chunk过滤
→ Neo4j节点/路径查询范围
→ RAG/KAG只使用有权限的上下文
```

如果前端隐藏了文档，但 ES、RAG 或 Neo4j 查询没有过滤权限，LLM 仍可能把无权限内容回答给用户。这是企业知识库中比普通权限 CRUD 更严重的数据泄漏风险。

当前 RAG 请求 DTO 中虽然声明了部分过滤字段，但控制器到检索服务的链路尚未完全接通，因此后续学习第 23、25、35 章时需要专门核对权限条件是否真正落到 ES 查询中。
