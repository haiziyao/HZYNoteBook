## 二、主链路

```text
客户端
  → kb-gateway（路由、鉴权、统一响应）
  → kb-user-auth / kb-document
  → MySQL 保存元数据
  → MongoDB 保存 Markdown 正文
  → 提交审核
  → RabbitMQ：通知、操作日志
  → kb-foundation：通知入库 + WebSocket 推送
  → 审核通过后异步调用 kb-ai、kb-search
  → RAG 向量块、KAG 图谱、ES 文档索引
```

## 三、面试回答模板

### 为什么拆成多个微服务？

按业务能力拆分：网关负责入口治理，用户服务负责认证，文档服务负责核心元数据，AI 服务负责 RAG/KAG，搜索服务负责 ES，基础服务负责通知/配置/日志。这样可以独立扩容和发布；代价是网络调用、数据一致性和链路追踪更复杂。

### 为什么不把正文全部放 MySQL？

MySQL 适合结构化元数据和事务查询，MongoDB 适合大段 Markdown 文本及版本内容。当前用 `content_id` 和 `documentId` 建立关联，获得存储解耦；代价是跨库事务需要补偿或重试。

### 审核通过后为什么异步建索引？

审核接口只需先完成状态变更，RAG 切块、Embedding、KAG 抽取和 ES 写入耗时较长，异步化可以缩短用户等待并隔离 AI/搜索故障。必须配合任务状态、重试和幂等，否则会出现“已发布但暂时搜不到”的最终一致状态。

## 四、不能忽略的设计点

- 文档状态要区分“文档状态”和“审核结果”：文档状态为 `0-草稿`、`1-已发布`、`2-已归档`、`3-待审核`；审核结果通常为 `1-通过`、`2-驳回`，驳回后文档退回草稿。
- `BaseEntity`：雪花 ID、自动填充、逻辑删除。
- `@OperationLog` + RabbitMQ：日志不是独立日志微服务，而是异步写入 `kb_operation_log`。
- 通知：先写 MySQL，再尝试 WebSocket；离线用户上线后补拉未读消息。
- Redis：系统配置 Hash，服务读取频繁配置时避免每次查 MySQL。
- RAG 与 ES：RAG 搜索文本块/向量，ES 普通索引搜索整篇文档。
- KAG：实体、关系写入 Neo4j，支持关联展示和图谱检索。
- 逻辑删除：MP 自动在查询中追加未删除条件，但删除值/未删除值要与全局配置和字段约定一致。
- 跨库一致性：MySQL、MongoDB、ES、Neo4j 没有一个本地事务覆盖全部步骤。
